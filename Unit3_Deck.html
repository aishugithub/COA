The assembly line

Analogy · A car takes hours to build, yet one rolls off the line every few minutes. The trick isn't a faster station — it's never letting a station stand idle. That is pipelining.
  • An assembly line has dedicated stations: body, paint, engine, test.
  • While one car is painted, the next is having its body built — every station always busy.
  • A processor does the same: while Ij decodes, fetch Ij+1; while Ij computes, decode Ij+1, fetch Ij+2.

Pipeline organization — the five stages as hardware

Under the hood · Each stage is separate hardware. Between them sit registers — the interstage buffers B1–B4 — that latch one instruction's work and hand it to the next stage.
Figure 6.2 — A five-stage pipeline built from stage hardware and interstage buffers.

What each buffer hands forward

Follow the work · Each buffer carries exactly what the next stage needs — data, register identifiers, and the control signals that tell that stage what to do.
  • B1 → the newly fetched instruction, ready to decode.
  • B2 → operands read from registers, the immediate value, and the control signals for later stages.
  • B3 → the ALU result (or the address / data for a memory access).
  • B4 → the value to be written back into the register file.
  • Control signals travel with the instruction — this is pipelined control (revisited in Chapter 6).
🎤 Ask the class
Predict · Before we count — trust the staircase you just saw.
3 instructions, 5 stages each. How many clock cycles —
running one at a time, versus pipelined?
Sequential: 3 × 5 = 15 cycles  ·  Pipelined: 5 + (3 − 1) = 7 cycles
🔑
Pipelining does not make one instruction faster.
It raises throughput by overlapping many, across dedicated hardware stages.
CHAPTER 2

Pipeline Performance
If overlapping k stages lets a new instruction finish every cycle, how much faster is that, really — and what stops us reaching the full k-fold gain?
Hamacher §6.8 · Performance evaluation (the basics)

Counting the cycles

The payoff · A pipeline of k stages fills up in k cycles, then finishes one instruction per cycle. Put numbers to the staircase.
  • k stages, n instructions → k + (n − 1) cycles  versus  k × n with no overlap.
  • Concrete: n = 100, k = 5 → 104 cycles instead of 500  ≈  4.8× faster.
  • Speedup approaches k (the number of stages) as n grows large.

The basic performance equation

Formally · Execution time depends on how many instructions run, the average cycles each takes, and the clock rate. Throughput is instructions completed per second.
T = ( N × S ) / R N = instructions · S = average cycles per instruction · R = clock rate
Throughput  Pnp = R / S  →  ideal pipeline (S = 1):  Pp = R Non-pipelined S = 5; ideal pipelining drops S to 1 → up to a 5× throughput gain.

How deep should the pipeline be?

Diminishing returns · An n-stage pipeline promises up to n× throughput. So why not 50 stages? Each extra stage brings costs that scale against depth.
  • More stages → less work per stage → shorter clock period → higher clock rate.
  • But more instructions in flight → more dependencies → more stalls.
  • And the branch penalty grows if the decision moves to a later stage.
  • The clock is ultimately limited by the slowest basic operation (usually the ALU). Real designs: ~10–20 stages.
🔑
Ideal speedup approaches the number of stages.
Every stall pulls the real gain below that ideal — which is what the rest of the unit is about.

Data Hazards
The staircase assumed every instruction is independent. But real code chains — one instruction's result feeds the next. What happens when the value isn't ready in time?
Hamacher §6.3 – §6.5 · Data dependencies, forwarding, memory delays

A dependency between neighbours

The catch · The destination of one instruction is a source of the next. Register R2 carries data from the Add to the Subtract — a data dependency.
Add     R2, R3, #100    R2 ← [R3] + 100
Subtract R9, R2, #30    R9 ← [R2] − 30
  • R2 is produced by the Add and consumed by the Subtract.
  • The Add writes R2 in cycle 5, but the Subtract reads it in cycle 3 — a read-before-write. Fine when run one at a time; the trouble starts when we overlap them…

Instruction (Control) Hazards
A data hazard made one instruction wait. A branch is nastier: the pipeline doesn't even know which instruction to fetch next — so it may fetch the wrong ones entirely.
Hamacher §6.6 · Branch delays & branch prediction

The pipeline fetches ahead — and may guess wrong

The gap · To stay full, the pipeline fetches the next in sequence every cycle. But a branch can redirect execution — so those already-fetched instructions may be wrong.
  • A branch changes which instruction runs next (loops, if-else, calls).
  • But the branch must be executed before we know the outcome and the target address.
  • Meanwhile the pipeline has already fetched the instructions behind it — which must be discarded. That waste is a control hazard.

Conditional branches — test early too

One more move · For a conditional branch such as Branch_if_[R5]=[R6] LOOP, the comparison must also be done early.
  • Move the comparator into the Decode stage — it uses the register-file outputs directly.
  • Now the branch decision and the target address are both known at the end of Decode.
  • This gives a common one-cycle penalty for all branch instructions.

Static prediction — a fixed guess

Simplest first · Guess the same way every time, decided before the program runs. If right, no penalty; if wrong, pay the penalty and refetch.
  • Assume not-taken: keep fetching in sequence — but only ~50% right for a coin-flip branch.
  • Use the branch direction: a backward branch (loop end) is usually taken; predict by the sign of the offset.
  • A single hint bit in the instruction lets the compiler say "expect taken / not-taken".

Dynamic prediction — learn from history

Do better · Track how this branch behaved last time. A 2-bit counter needs two wrong guesses in a row to change its mind — so one odd iteration won't fool it.
Figure 6.12 — A 2-bit predictor: it only flips its guess after two misses in a row.
🎤 Ask the class
Predict · A loop runs 100 times — its branch is taken 99 times, not-taken once (the exit).
With the 2-bit predictor, about how many of those 100 branches are mispredicted?
Just ~1 — the loop exit. The single not-taken pass isn't enough to flip a strongly-taken counter, so every looping pass is predicted correctly.

Predicting in cycle 1 — the branch target buffer

The last piece · To fetch the right instruction next cycle, we must predict while still fetching the branch — before we even know it's a branch.
  • A branch target buffer (BTB) is a small fast table, keyed by the branch's address.
  • Each entry stores the prediction state bits and the target address.
  • While fetching, a BTB hit gives both "this is a taken branch" and where to go — so the right instruction is fetched next cycle. (~1024 entries, most-recent branches.)
🔑
Control hazards shrink three ways:
decide early, fill the delay slot, and predict the branch.

Influence on Instruction Sets
The pipeline runs smoothest on simple, regular instructions. So the desire to pipeline actually reshaped how instruction sets are designed — that's the RISC story.
Hamacher §6.10 · Pipelining and the instruction set

Simple instructions vs complex ones

Design for the pipe · The five-stage pipeline was tailored to RISC-style instructions. Regularity keeps Fetch and Decode fast and every stage predictable.

RISC — pipeline-friendly

  • Uniform length (one word), few formats → fast Fetch/Decode
  • Load–Store: only Load/Store touch memory; arithmetic is register-to-register
  • Simple, regular addressing → simple operand-stage control

CISC — pipeline friction

  • Variable length → several cycles just to fetch
  • Multiple memory operands per instruction
  • Complex addressing → side effects & condition codes

Side effects fight the pipe

The friction · A side effect changes a location other than the named destination — an extra, hidden dependency the hardware must catch.
Move R5, (R8)+    auto-increment
Writes R5 and also changes R8.
  • A later instruction using R8 now has a dependency needing extra stall / forward logic.
  • Condition codes are another side effect: a Compare sets flags that a later Branch silently depends on.
  • Modern CPUs keep CISC instruction sets but crack each into simple RISC-like micro-operations internally.
🔑
The instruction set and the pipeline are designed together.
Simplicity and regularity are what make overlap pay off.
CHAPTER 6

Datapath & Control Considerations
Overlap only works if no two stages ever fight over the same hardware — and if we can put honest numbers on every stall we've met.
Hamacher §6.2, §6.7, §6.8.1 · Structural hazards & quantified penalties

Every stage needs its own hardware

Why · If two stages shared a unit, they couldn't both work in the same cycle — the overlap would be lost. So the datapath is replicated per stage.
  • Separate hardware in each stage → all five instructions advance simultaneously.
  • Each stage owns a buffer register (B1–B4) to hold its result for the next stage.
  • Pipelined control: control signals are generated in Decode and travel with the instruction down the pipe.

Structural hazard — two stages, one resource

The clash · A single memory serves both Fetch (every cycle) and Memory access (for loads/stores). In the same cycle they collide — one must stall.
§6.7 — Separate instruction & data caches remove the structural hazard.

Putting numbers on the stalls

Honest accounting · The ideal is S = 1. Each kind of stall adds a penalty term — and these terms simply add up (Hamacher §6.8.1).
S = 1 + δstall + δbranch + δmiss
  • δstall (load-use) e.g. 0.25 × 0.40 × 1 = 0.10  ·  δbranch e.g. 0.20 × 0.10 × 1 = 0.02
  • δmiss (cache — often the biggest) e.g. (0.05 + 0.30 × 0.10) × 10 = 0.8
  • Example 6.2: 20% branches, not-taken prediction. 30% taken → S = 1.06; 70% taken → S = 1.14; speedup = (1.14/1.06 − 1) ≈ 7.5%.
🔑
Give every stage its own hardware, duplicate shared resources that clash —
and remember the cache-miss penalty usually dominates.

Superscalar Operation
A single pipeline can finish, at best, one instruction every cycle. To go faster still, we stop waiting in one line — and open several checkouts at once.
Hamacher §6.9 · Multiple issue & out-of-order execution

Multiple issue — more than one per cycle

Break the ceiling · A superscalar processor equips itself with several execution units and issues multiple instructions each cycle.
  • Fetch and decode two or more instructions every cycle into an instruction queue.
  • A dispatch unit sends independent instructions to different execution units.
  • Throughput can exceed one instruction per cycle — this is multiple-issue.

The organization · Two execution units — an arithmetic unit and a two-stage Load/Store unit — fed from a shared queue by the dispatch unit.

Keeping many-in-flight correct

The price · With several units running at once, instructions may finish out of order. Extra hardware keeps the results correct and exceptions precise.
  • Reservation stations hold a dispatched instruction until all its operands arrive.
  • Out-of-order execution: independent instructions run as soon as they're ready.
  • Register renaming uses temporary registers to avoid false conflicts.
  • A reorder buffer commits results in program order → precise exceptions.
