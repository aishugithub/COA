1. The Pipelining Idea

Hamacher §6.1 – §6.2

1.1 Why pipelining?

  • A program can be made faster in two broad ways:
    • use faster circuitry, or
    • arrange the hardware so that more than one operation happens at the same time.
  • Pipelining takes the second route — it overlaps the execution of successive instructions.
  • Analogy — the assembly line: a car takes hours to build, yet a finished car rolls off the line every few minutes, because every station is always working on a different car.

1.2 One instruction = five steps (recall from Unit 2)

  • A single instruction executes in five steps: Fetch → Decode → Compute → Memory → Write (5 clock cycles).
  • Each step uses different hardware.
  • So the moment instruction Ij leaves Fetch and enters Decode, the Fetch unit is free — it can fetch Ij+1 right away.
  • Overlapping the steps of successive instructions across dedicated hardware stages is pipelining.

1.3 The ideal case

  • Three instructions are overlapped so that every stage is busy with a different instruction (see figure).
  • Any one instruction still takes 5 cycles start-to-finish, but once the pipeline is full, a new instruction completes every cycle.

Key idea. Pipelining does not make one instruction faster. It increases throughput — instructions completed per unit time — by overlapping many instructions.

1.4 Pipeline organization & interstage buffers

  • Each of the five stages is separate hardware.
  • Between consecutive stages sit registers called interstage buffers (B1–B4).
  • At the end of every clock cycle, each buffer latches its stage's result so the next stage can use it in the following cycle.
  • The buffers carry data, register identifiers and the control signals for later stages.
Figure 6.2 — A five-stage pipeline (stage hardware + interstage buffers B1–B4).
  • B1 → the newly fetched instruction, ready to decode.
  • B2 → the two operands read from registers, the immediate value, and the control signals for later stages.
  • B3 → the ALU result (data to write, or an address/data for memory).
  • B4 → the value to be written back into the register file.
  • Control signals travel with the instruction down the pipe — this is pipelined control.

2. Pipeline Performance

Hamacher §6.8 (basics)

2.1 Counting the cycles

  • Take a pipeline of k stages executing n instructions.
  • The first instruction needs k cycles to reach the end; after that, one completes each cycle.
  • Total time = k + (n − 1) cycles  —  compared with k × n cycles with no overlap.
  • Example: k = 5, n = 100 → 104 cycles instead of 500 (≈ 4.8× faster).
  • As n grows large, the speedup approaches k (the number of stages).
Worked example A 5-stage pipeline (k = 5) runs a loop with n = 20 independent instructions. Cycles needed = k + (n − 1) = 5 + 19 = 24 cycles. Without pipelining it would take k × n = 5 × 20 = 100 cycles. Speedup = 100 / 24 ≈ 4.17× — close to, but below, the ideal 5× because n is still small; as n grows the answer creeps closer to k.
→ Go deeper, with more worked examples, in the Foothold course — open Module 3 → 3.2 The Pipeline Idea & Performance Optional — only if you want to go deeper. Not needed for the exam.

2.2 The performance equation

  • For a program with dynamic instruction count N:
T = ( N × S ) / R
N = number of instructions · S = average cycles per instruction · R = clock rate
  • Throughput = instructions executed per second:
Pnp = R / S   →   ideal pipeline (S = 1): Pp = R
  • Non-pipelined: S = 5. Ideal pipelined (no stalls): S = 1 → up to a 5× throughput gain.

2.3 How many stages?

  • More stages → less work per stage → shorter clock period → higher clock rate.
  • But more instructions in flight → more dependencies → more stalls.
  • And the branch penalty grows if the branch decision moves to a later stage.
  • The clock is limited by the slowest basic operation (usually the ALU).
  • Gains diminish beyond a point — real designs use ~10–20 stages at several GHz.
Key idea. Ideal speedup approaches the number of stages; every stall pulls the real gain below the ideal — which is what the hazards (next) are about.

3. Data Hazards

Hamacher §6.3 – §6.5

3.1 The data dependency

  • The ideal overlap assumes instructions are independent — real code often chains them.
  • Example: Add R2,R3,#100 then Subtract R9,R2,#30.
    • R2 is produced by the Add and consumed by the Subtract — a data dependency.
    • The Add writes R2 in cycle 5 (Write), but the Subtract reads it in cycle 3 (Decode) — a read-before-write.
  • Any condition that forces the pipeline to wait is a hazard; this one is a data hazard. This particular kind — a later instruction depending on an earlier one's result — is called a RAW (Read-After-Write) hazard.
ExplanationThe name "Read After Write" can feel backwards right after reading "read-before-write" above — but the two phrases describe two different things. RAW names the dependency: in correct program order, the Write must happen, then the Read happens after it — that's simply what "R2 is produced by the Add and consumed by the Subtract" means. The hazard is that pipelining breaks this order — the Subtract's Decode tries to read R2 before the Add's Write has actually happened. So the dependency is named for the order that should hold (Write, then Read); the hazard is that the pipeline lets the Read jump ahead of it. The same logic gives WAR (Write-After-Read) and WAW (Write-After-Write) hazards elsewhere in the course.

3.2 The simplest cure — stall

  • Stall the Subtract in Decode until R2 is written — here for 3 cycles.
  • Each idle cycle inserted is a bubble; all following instructions are delayed too.

ExplanationLook carefully at the diagram: the Subtract's D box (cycle 3) is followed by only two cells marked "bubble" (cycles 4 and 5) — yet we call this a 3-cycle stall. Both numbers are correct; they're just counting different things. Cycle 3 was already going to be Subtract's normal Decode cycle — it isn't "extra" time. Cycles 4 and 5 are the two additional idle cycles forced in because R2 isn't ready yet — those are the two bubbles you see drawn. Add them together — cycle 3 (held) + cycle 4 (bubble) + cycle 5 (bubble) — and Subtract is stuck in Decode for a total of 3 cycles before it can move to Compute in cycle 6. So: 2 bubbles = the extra delay injected; 3 cycles = the full time spent stalled. If you check this same example on the AVPS simulator, its own numbers agree exactly — it also stalls for 3 cycles — but because the simulator advances one cycle at a time, you'll only ever see up to two bubble cards on screen together at once (the third stalled cycle's bubble hasn't reached the next stage yet). That's a feature of how the animation plays out, not a disagreement with the textbook.

3.3 Operand forwarding — the better cure

  • The value the Subtract needs actually exists earlier than the register write.
  • The Add's ALU produces R2 at the end of cycle 3 and it is captured in register RZ.
  • Operand forwarding: route the result directly from RZ to the ALU input where it is needed — no stall.

4. Instruction (Control) Hazards

Hamacher §6.6

4.1 The branch problem

  • To stay full, the pipeline fetches the next in sequence every cycle.
  • A branch can redirect execution — but it must be executed before we know the outcome and target.
  • The instructions already fetched behind it may be wrong and must be discarded — a control (instruction) hazard; the lost cycles are the branch penalty.

4.2 The branch penalty, and reducing it

  • If the target is computed in the Compute stage: two instructions are fetched wrongly → 2-cycle penalty.
  • Branches are ~20% of instructions, so a 2-cycle penalty could add up to ~40% — worth attacking.

4.3 The branch delay slot

  • The instruction location right after a branch is the branch delay slot — it is fetched anyway.
  • Idea: always execute it, and let the compiler move a useful instruction there.
  • Branching then takes effect one instruction later — delayed branching.
  • Compilers fill the slot usefully about 70% of the time (else a NOP is used).

4.4 Branch prediction

  • Static prediction — same guess every time:
    • Assume not-taken — keep fetching in sequence (~50% right for a random branch).
    • Use direction — a backward branch (loop end) is usually taken; predict by the sign of the offset.
    • A compiler-set hint bit can say "expect taken / not-taken".
  • Dynamic prediction — learn from recent behaviour with a 2-bit saturating counter (four states):
    • States: Strongly-Not-Taken, Likely-Not-Taken, Likely-Taken, Strongly-Taken.
    • Predict taken in the two "taken" states, not-taken in the two "not-taken" states.
    • It takes two wrong guesses in a row to flip — so one odd iteration won't fool it. For a loop run many times, only the exit pass is mispredicted.
Figure 6.12 — A 2-bit predictor: it flips its guess only after two misses in a row.
  • Branch target buffer (BTB): to predict in cycle 1 (while still fetching the branch), a small fast table keyed by the branch address stores the prediction state bits and the target address. A hit tells the processor "this is a taken branch" and where to go, so the right instruction is fetched next cycle (~1024 entries).
Key idea. Control hazards shrink three ways: decide the branch early, fill the delay slot with useful work, and predict the branch (static, dynamic 2-bit, and the BTB for cycle-1 prediction).

5. Influence on Instruction Sets

Hamacher §6.10

5.1 Pipelining rewards simple instructions

  • The five-stage pipeline is tailored to RISC-style instructions; the wish to pipeline actually shaped instruction-set design.
  • RISC — pipeline-friendly:
    • Uniform length (one word), few formats → simple, fast Fetch and Decode.
    • Load–Store architecture: only Load/Store touch memory; arithmetic is register-to-register → predictable timing.
    • Simple, regular addressing → simple operand-stage control.
  • CISC — pipeline friction:
    • Variable length → several cycles just to fetch.
    • Multiple memory operands per instruction → extra stalls.
    • Complex addressing → side effects and condition codes.

5.2 Side effects and condition codes

  • A side effect changes a location other than the named destination.
  • Example: Move R5, (R8)+ (autoincrement) writes R5 and also changes R8 — a hidden dependency that needs extra stall/forward logic.
  • Condition codes are another side effect: a Compare sets flags that a following Branch silently depends on.
  • Modern CPUs keep CISC instruction sets but internally crack each into simple RISC-like micro-operations.
Key idea. The instruction set and the pipeline are designed together. Simplicity and regularity — uniform length, load-store, simple addressing — are what let overlapping pay off.

6. Datapath & Control Considerations

Hamacher §6.2, §6.7, §6.8.1

6.1 Per-stage hardware and pipelined control

  • Each stage must have its own hardware — if two stages shared a unit, they couldn't both work in one cycle and the overlap would be lost.
  • Each stage owns a buffer register (B1–B4) to hold its result for the next stage.
  • Pipelined control: control signals are generated in Decode and travel with the instruction down the pipe.

6.2 Structural hazards

  • A structural hazard occurs when two stages need the same hardware resource in the same cycle.
  • Classic case: a single cache serves both Fetch (every cycle) and Memory access (loads/stores). Together they collide → one must stall.
  • Remedy: provide separate instruction and data caches so Fetch and Memory proceed together.
§6.7 — Separate instruction & data caches remove the structural hazard.

6.3 Putting numbers on the stalls

  • The ideal is S = 1. Each kind of stall adds a penalty term, and the terms are additive:
S = 1 + δstall + δbranch + δmiss
  • δstall (load-use): e.g. 0.25 × 0.40 × 1 = 0.10.
  • δbranch (mispredict): e.g. 0.20 × 0.10 × 1 = 0.02.
  • δmiss (cache — often the biggest): e.g. (0.05 + 0.30 × 0.10) × 10 = 0.8.
EXAMPLE 6.2
  • Given: 20% branches, static not-taken prediction (1-cycle penalty), no other stalls.
  • 30% taken → δbranch = 0.20 × 0.30 = 0.06 → S = 1.06.
  • 70% taken → δbranch = 0.20 × 0.70 = 0.14 → S = 1.14.
  • Speedup of the faster case = (1.14 / 1.06 − 1) × 100 ≈ 7.5%.
Key idea. Give every stage its own hardware and duplicate the shared resources that would clash; when you put numbers on the stalls, the cache-miss term usually dominates.

7. Superscalar Operation

Hamacher §6.9

7.1 Multiple issue

  • A single pipeline tops out at one instruction per cycle.
  • A superscalar processor has several execution units and issues multiple instructions each cycle (multiple-issue).
  • A fetch unit fetches 2+ instructions per cycle into an instruction queue; a dispatch unit sends independent instructions to different execution units.

7.2 Keeping many-in-flight correct

  • With several units running, instructions may finish out of order; extra hardware keeps results correct and exceptions precise:
  • Reservation stations — hold a dispatched instruction until all its operands arrive.
  • Out-of-order execution — independent instructions run as soon as they are ready.
  • Register renaming — temporary registers avoid false conflicts.
  • Reorder buffer — commits results in program order → precise exceptions.

7.3 The three hazards — summary

  • Data hazard — cause: an instruction needs a result not yet produced. Remedy: forwarding; stall; instruction scheduling.
  • Control (instruction) hazard — cause: branch outcome/target not yet known. Remedy: decide early; delay slot; branch prediction + BTB.
  • Structural hazard — cause: two stages need the same hardware resource. Remedy: duplicate resources (separate I-cache / D-cache).
Key idea. Pipelining approaches one instruction per cycle; superscalar operation pushes past it to several per cycle. Realising the potential depends on the instruction set, the pipeline hardware, and the compiler working together.
