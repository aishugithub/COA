Register Transfers & Microoperations

In Unit 1, Load moved a word to a register. But how does one bit actually cross from one register to another? We start at the smallest step of all.

Core

From boxes to the steps inside them

Where this fits · Unit 1 named the CPU's parts. This chapter opens them up and asks how one instruction is actually carried out inside.

Unit 1 gave us

Five units, a bus, registers (PC, IR, MAR, MDR), and instructions like Load, Add, Store.

Unit 2 asks

What tiny hardware steps carry out each of those instructions — and what raises the signals that drive them?

The smallest such step has a name: the microoperation.

Core

The microoperation — one elementary step

Why now · We keep saying “a step.” Let's pin down the smallest step there is — and separate it from the instruction that commands it.

A microoperation is an operation on register data, carried out in one clock pulse.

Instruction — what the programmer writes

One command in the ISA: an opcode + operands.
ADD R1, R2  →  “R1 ← R1 + R2”.
Also LOAD, STORE — the Unit 1 instructions.

Register Transfer — only on a control signal

The gap · The notation says what moves. It never says when. A real register transfer must wait for a signal that says “now.”

P : R2 ← R1  — the transfer happens only if control signal P = 1.

If P = 0 the wires still carry R1's value — but R2's load line stays shut, so nothing moves. Control turns a permanent connection into a timed transfer.

Core

The common bus — built from multiplexers

What we want · A single shared path any register can send to — instead of a private wire between every pair. Goal first: one bus, many sources. The multiplexer is our first way to build it.

The select lines alone decide which register reaches the bus — flip S1S0 and a different value rides across. For k registers of n bits: n multiplexers, each k×1.

Core

The common bus — built from tri-state buffers

Same goal, cheaper · We want that one shared bus again — but multiplexers cost gates for every source. A leaner route: give each register a three-state buffer onto the line.

A buffer's third state — high-impedance — lets many outputs share one wire while all but one stay electrically absent.

Enable two at once and they fight for the same line — bus contention, an invalid value. A decoder guarantees exactly one enable is high.

Core

Memory transfers: Read and Write

One step further · Registers can now reach each other over the bus. But programs and data live in main memory — so the CPU must be able to reach across to it too.

Address in MAR, data in MDR — all data to and from memory passes through MDR.

Read — fetch a word

MDR ← M[MAR]
put the address in MAR, raise Read; memory copies that word into MDR.

Write — store a word

MDR ← R1,  M[MAR] ← MDR
the data first moves R1 → MDR, then MDR is written to the addressed word.

R1 never reaches memory directly — it must go through MDR. (Mano names these AR / DR.) This is the syllabus's "fetching a word, storing a word."

Arithmetic, Logic & Shift Microoperations

We can move bits around. But moving isn't computing. How do the same set of wires add, subtract, AND, and shift — and become the ALU?

Core

The operations an ALU must do — and one question

From moving to computing · Chapter 1 could only move bits — and moving isn't computing. Now the ALU has to actually operate. Here is the full menu — but must each one have its own hardware?

+−×÷ +1−1

Six operations → six circuits?

Start with ×. Multiplying is nothing but repeated addition: 3 × 4 means add 3, four times.

So × needs no new box — just the adder, used repeatedly. And ÷? Repeated subtraction…

…but can the same adder go the other way and subtract?

Core

Subtract without a subtractor — the method of complements

The other direction · We just saw one adder cover × by repeating. But repeating only ever adds. To subtract we seem to need new hardware — unless we can turn a subtraction into an addition.

The trick: A − B = A + (2's complement of B). And 2's complement is easy — flip every bit, then add 1.

What we want

5 − 3 = 2

The magic — binary 2's complement

Take 3 = 0011 → flip → 1100 → +1 → 1101
Now just add: 0101 + 1101 = 1 0010
Throw away the carried 1 → 0010 = 2 ✓  same answer, using only addition

Both are the same move, and both are free in hardware: flipping is one XOR per bit — a controlled NOT, so M chooses flip or pass — and the "+1" is just setting the adder's carry-in = 1.

Who thought of this? The method of complements is centuries old — decimal adding machines used it. John von Neumann proposed two's complement for binary computers in his 1945 EDVAC report; the 1949 EDSAC was the first to use it. Next: our adder doing exactly this.

Core

The adder–subtractor: one circuit, two jobs  — try A = 5, B = 3

From numbers to gates · The numbers just proved it — subtracting is adding the 2's complement. Now watch our own adder do exactly that: flip B, set carry-in = 1, same box.

One M does both: it feeds every B-XOR and the carry-in — so Cin = 1 is exactly the "+1" that makes B̅ a full 2's complement.

Core

One adder + one MUX = many operations

The payoff · Our adder already subtracts. Put a MUX on its second input Y and let the control unit choose the word — now the same box does add, subtract, increment, decrement. Press a button and watch the signals.

Press a button in the Control Unit — the select line S1S0 picks the MUX word and sets Cin; the chosen path lights up green and stays lit. (A = 5, B = 3 · use → to continue)

Core

Bitwise microoperations — what they are, and why

A different need · Arithmetic treats the whole word as one number. Logic works the other way — on the individual bits. When would we ever need that? Here is the everyday reason.

What. A logic (bitwise) microoperation lines up two words and applies a Boolean op — AND, OR, XOR, NOT — to each bit position on its own, not to the word as a number.

Why. A control / status register packs many one-bit flags into a single word:

0

1ENABLE
0
1READY
0ERROR
1
1

To report a fault we must set the ERROR bit → 1; once handled, clear it → 0 — while every other flag stays exactly as it was.

Change one bit, leave its neighbours alone. A plain overwrite can't — bitwise ops can.

Core

How — OR sets a bit, AND clears a bit

Change one, keep the rest · So we must flip one flag and leave its neighbours untouched. A mask — a second word we choose — marks which bits to touch; the logic op does the rest.

Mask (AND) → clear a flag

Turn one flag off without disturbing the rest. Flags 1011, clear the ERROR bit: AND 1101 (a 0 only there) = 1001. ERROR → 0, the others untouched.

Set (OR) → set a flag

Turn one flag on without disturbing the rest. Flags 1001, set the READY bit: OR 0100 (a 1 only there) = 1101. READY → 1, the others untouched.

Partners on the same idea: selective-clear = AND with a complemented mask, toggle = XOR, and NOT just inverts every bit — all of them appear in the full sixteen-operation list ahead.

Core

Worked: AND clears bits, OR sets bits

See it on a byte · A mask is a second word we choose. AND it in to keep or clear bits; OR it in to force bits to 1. Watch each on the same 8-bit value.

AND — mask / clear

1011 0110 (182)
AND0000 1111 (mask)
=0000 0110 (6)

Where the mask is 0 the bit is cleared; where it is 1 the bit passes. → extract the low nibble, or test one bit.

OR — set

1011 0000
OR0000 1111
=1011 1111

Where the mask is 1 the bit is forced to 1; where it is 0 the bit is left alone. → turn on flags / GPIO pins.

Same trick, opposite jobs: AND with 0 knocks bits down, OR with 1 lifts bits up.

Core

Worked: extract a field, insert a field

What masking is for · A word often holds a small field packed inside it. Extract = copy that field out as a value. Insert = write a new value into that field, leaving every other bit alone. Take the byte 1011 0110 — high nibble = flags, low nibble = a mode field.

Extract the mode (read it out)

1011 0110 (word)
AND0000 1111 (keep the field)
=0000 0110 → mode = 6

Everything outside the field is masked to 0, so the field stands alone as a value. (If it sat higher up, shift it down to read it.)

Insert mode = 1010 (write it in)

①clear1011 0110 AND 1111 0000
= 1011 0000
②place1011 0000 OR 0000 1010
= 1011 1010

Clear the field with AND, then OR the new bits in. Mode is now 1010; the flag nibble 1011 is untouched.

Extract = AND to isolate the field. Insert = AND to clear the field, then OR to drop the new bits in — same mask idea, opposite direction.

Core

Why these bit-level operations matter

The next level up · Each logic op touches one bit — humble on its own. But they are the primitives that bigger operations are built from. Here is what they buy us.

Masking — pick out bits

AND with a mask clears the bits you don't want; OR sets the ones you do. That is how a field is extracted or inserted inside a word.

Flags & control bits

Set / clear / test one bit — status-register flags, permission bits, an IoT GPIO pin driven high or low.

Shifts do arithmetic — almost free

Left shift = ×2, right shift = ÷2; multiply / divide is shift-and-add. A shift is just rewiring — one clock pulse, no adder — so it costs the hardware almost nothing next to a full multiply.

…and bigger systems

Packing fields, checksums / CRC, hashing, encryption, and graphics colour maths — all stand on these bit ops.

Individually humble, collectively the foundation of everything above the gate.

And they are cheap: each logic op or shift is a single ALU clock pulse — which is exactly why we let the ALU do them, and why multiply / divide are built from shifts.

Core

Why exactly sixteen? — an operation is a set of answers

What an op really is · With two input bits there are only four possible situations: 00, 01, 10, 11. A logic operation is just a rule that answers one question for each — output 0 or 1?

Take AND: its rule is "say 1 only when both are 1." That is four answers — 0, 0, 0, 1 — one for each situation. Those four answers are the operation.

Stack the four answers into a code: AND = 0001. A different rule → a different code: OR = 0111 ("1 unless both are 0").

Four answers, each independently 0 or 1 — like four on/off switches. Multiply the choices (not 4 × 2 = 8):  2×2×2×2 = 24 = 16

The four mixed codes (e.g. 1011 = x + y', i.e. A ∨ B̅) have no everyday gate name — but they're real functions with real uses: x · y' (A ∧ B̅) is selective-clear (clear only the bits B marks), and x + y' is logical implication. We list all sixteen because 24 is every possible rule; hardware just names the handful worth exposing and builds the rest by combining.

Sixteen operations, four gates — one gate underneath

How few we really need · We do not build sixteen circuits. Every one of the sixteen is a combination of just four logic operations — and those four are themselves built from a single universal gate.

★ Build only AND, OR, XOR, NOT — the other twelve are combinations of these four.

What the ALU offers

Four operations — AND, OR, XOR, NOT — picked by a MUX. The other twelve are just combinations of these.

What it's built from

One universal gate: NAND alone can build all four — and the adder and the MUX too. NAND is the brick; these four are what we assemble from it.

Two levels, don't confuse them: four operations = what the machine offers; one gate (NAND) = what silicon is made of.

Core

A shift, in two little steps

Slow it down · A shift is really two actions. Let's left-shift the word 0110 one place, doing each action on its own so it's clear what moves and what enters.

So a shift = ① move every bit one place, then ② fill the vacated end. The only question left is what fills that end — next.

Core

What fills the vacated end? — three kinds of shift

The one difference · Every shift moves the bits the same way. The three types differ only in step ② — what slides into the empty end — and that one choice decides what the shift means.

Left shift ≈ ×2, right shift ≈ ÷2 — a shift is far cheaper than a full multiply.

Who thought of this? Doubling-and-adding to multiply is ancient — Egyptian multiplication (Rhind papyrus, ~1550 BCE) and Russian-peasant multiplication both use it. It becomes a literal shift only in the binary system (Leibniz, ~1703). It predates Boolean algebra and von Neumann — they only built it into hardware.

Core

Worked: a shift multiplies or divides by 2

Prove it on numbers · Just like 2's-complement subtraction, let's see the arithmetic actually happen — decimal beside binary — so "left ≈ ×2, right ≈ ÷2" stops being a slogan.

Shift left → double it (×2)

5 =0000 0101 (5)
<<10000 1010 = 10  (×2)
<<10001 0100 = 20  (×2 again)

Each left shift slides every bit up one place — worth twice as much — and a fresh 0 enters at the right. 5 → 10 → 20.

Shift right → halve it (÷2)

20 =0001 0100 (20)
>>10000 1010 = 10  (÷2)
>>10000 0101 = 5  (÷2 again)

Each right shift slides every bit down one place — worth half. 20 → 10 → 5. But a negative number breaks this — see the next slide.

Shifting by k = ×2k or ÷2k — one cheap operation instead of a full multiply or divide.

Core

Why arithmetic shift-right is special

A doubt to settle · We just halved 20 → 10 → 5 by shifting right. Try the negative case: divide −20 by 2 the same way — shift right and feed a 0 into the top bit. Does it still work?

Take the signed byte 1110 1100 — that's −20 in two's complement.

That is the whole point of ashr: it re-inserts the sign bit instead of a 0, so dividing a negative number by 2 still gives a negative number.

Core

Multiplying, the smart way: shift-and-add

Back to slide 13 · "Multiply is repeated addition" works, but it ignores the structure of binary. Shift-and-add is smarter — it uses the multiplier's bits to decide which scaled copies of the multiplicand to add.

Repeated addition

5 × 3 = 5 + 5 + 5. Correct, but slow — the count of adds grows with the number, and it wastes the binary structure.

Shift-and-add

Read the multiplier's binary digits; for each 1, add a shifted copy of the multiplicand. Fewer, structured steps.

Exactly what a simple circuit can do: shift and add, bit by bit.

Core

Why it works — a number is a sum of powers of two

The key identity · Write the multiplier in binary as a sum of powers of 2. Then multiplying by it splits into a few multiply-by-a-power-of-2 — and each of those is just a shift.

3 = 011 means   3 = (1 × 21) + (1 × 20)
so   5 × 3 = 5 × (21 + 20) = (5 × 21) + (5 × 20)
And multiplying by 2n is a left shift by n places:
5 << 1 = 01010 = 10  (= 5 × 2)
5 << 0 = 00101 = 5  (just 5 itself)

Each product term is simply 5, shifted.

Core

Why this scales

Count the work · Shift-and-add does at most one add per bit of the multiplier — no matter how large the numbers are.

Repeated addition

"Add the multiplicand K times" → the number of adds grows with the value. A big multiplier = arbitrarily many additions.

Shift-and-add

An n-bit multiplier → at most n shifts + n adds. One potential add per bit — bounded by the number of digits, not the value.

This is essentially what a hardware multiplier does at the gate level.

Core

The mirror: division is shift-and-subtract

Run it backwards · Multiplication builds up a product by adding shifted copies. Division does the reverse — it strips away shifted copies of the divisor from the dividend, one bit at a time, from the most-significant bit down.

At each quotient bit position:
1 shift the divisor to line up with that position.
2 if the shifted divisor fits (subtracting won't go negative) → subtract, record a 1.
3 if it doesn't fit → record a 0, move on without subtracting.

Multiply asks

"Which shifted copies do I add to build the product?"

Divide asks

"Which shifted copies can I subtract out before the value hits zero?"

Same shift-based structure — opposite direction, opposite operation.

Core

The Arithmetic–Logic–Shift Unit — one example through every box

Fold them into one · Arithmetic, logic and shift all compute in parallel on A and B; a final MUX passes one result. Push A = 5, B = 3 through and watch each box.

select S3 S2: 00→Arithmetic · 01→Logic · 10→shift-right · 11→shift-left. The final MUX needs only 2 lines (S3 S2); S1 S0 + Cin choose the op inside the arithmetic/logic boxes → full ALU select = S3 S2 S1 S0 + Cin. One stage per bit; ×, ÷ are add/shift sequences, not a box.

Execution of Complete Instructions

You have moves (Ch 1) and an ALU (Ch 2) — loose pieces. But Add R4, R2, R3 is one line. How many hardware beats does it really take?

Core

The datapath — where operands flow

Where this fits · Chapter 2 built the ALU; now we ask where operands physically sit as an instruction runs. The datapath is the fixed lane of registers and wires data travels along. It introduces new interstage registers — RA, RB, RZ, RM, RY — each just parks a value between one step and the next. Watch the flow build, left to right.

Read it left→right: register file → RA/RB (operands) → ALU → RZ (result) → RY → back to the register file (port C); RM branches off for memory. Each interstage register simply holds a value for one step so the next step can use it.

Core

Every instruction rides the same five beats

1 · Fetch

Read the instruction at [PC]; increment the PC.

2 · Decode

Work out the operation; read source registers.

3 · Compute

ALU performs the op or computes an address.

4 · Memory

Read/write data — only for Load / Store.

5 · Write-back

Result returns to the destination register.

Core

Fetch: several micro-steps, or one beat?

A doubt to settle · In Unit 2 we fetched an instruction in several micro-steps — PC → MAR → memory → MDR → IR. Yet the five-beat slide calls Fetch one step. Both are right: it depends on the datapath. Same work, drawn two ways.

Same transfers either way — the word still travels PC → MAR → memory → MDR → IR. The single shared bus forces those steps into separate clocks; dedicated paths (a memory port + a PC adder) let them overlap and finish in one — if memory answers in one cycle; a slow memory still stalls.

Core

Trace one instruction: Load R2, A

Read it as · “Load into register R2 the value stored at memory location A.” Five beats turn that one line into hardware — each row shows the register transfers, then what they mean in plain words.

What is a “base register”? A register that holds a starting address. In an addressing mode like Load R2, 20(R5), R5 is the base and 20 the offset; step 3’s ALU adds them: effective address = [R5] + 20.  Our Load R2, A uses absolute addressing — A is the whole address, already in the instruction — so no base register is added and the ALU does no address calculation at all (the Compute beat is idle).

One assembly line → five ordered hardware steps, each one clock beat.

Core

When A isn’t the address: effective address = base + offset

Why a second example · Last slide, A was the whole address (absolute) — so nothing was read from a base register. More often the address lives in a register (a base) and the instruction adds an offset. Now Step 2’s “read base register” and Step 3’s ALU-add finally do real work.

Load R5, 20(R7)  =  “Load into R5 the value stored at address ( [R7] + 20 ).”  Here R7 = 1000 (base), offset = 20.

Commit to memory: the effective address is what the ALU builds in the Compute beat — effective address = [base register] + offset. Step 2 reads the base (R7) out of the register file; Step 3 adds the offset. Absolute addressing is just the special case where the instruction already carries the full address, so no register is added.

Why it matters: this is how you walk an array — keep the array’s start in the base register, change only the offset to reach each element — and how code stays relocatable.

Core

Why RY and that little multiplexer?

The tension · Two different instructions must write a register — Add makes its value in the ALU, Load brings it from memory. But the register file has only one write port. How do both reach it? They merge.

One uniform path

Every instruction’s write-back is just RY → destination register. The last beat never has to know where the value came from.

The mux is the chooser

It picks the ALU result for arithmetic, the memory data for a load. RY holds the winner.

RY latches the beat

RY also holds the value steady across the clock edge between the Memory beat and the Write-back beat, so each stage hands its result cleanly to the next.

Connect back: on the single-bus machine (Unit 1) there is no MuxY or RY — the shared bus carries MDR → register directly, one transfer at a time. RY exists only because this datapath splits work into five fixed one-clock stages.

Follow the numbers · the same five phases, now drawn on the datapath. ③ is the star — the ALU adds base + offset to build the address, the very same adder that does arithmetic. Every instruction crosses this path the same way, one after another.

③ is the beat that matters: the ALU adds [R7] + 4 to form the effective address in RZ — the same adder that computes [RA]+[RB] for an Add. Absolute loads skip this add; the address is already in the instruction.

The datapath and the five-step sequence.
  • Register file — two read ports (A, B), one write port (C).
  • Interstage registers — RA, RB (operands), RZ (ALU result), RM (memory data out), RY (data in).
  • Five steps — Fetch, Decode, Compute, Memory, Write-back.
  • Only Load / Store use the Memory step; arithmetic writes back a register.

One assembly line = a fixed rhythm of at most five beats.
Fetch, decode, compute, memory, write-back — the steady pulse behind every program.

Bus Organization

Our five-step trace worked — but on one bus, that means one move at a time. Can we re-wire the datapath to do more per beat?

Core

Single-bus — one shared highway

Cheap and simple — but adding two numbers means shuttling operands across the bus one at a time, so an ALU op spreads over several clocks.

Core

Three buses — two operands in, one result out, at once

Bus A and Bus B carry both operands to the ALU simultaneously; Bus C returns the result — the whole operation in one step.

?
Re-trace Add R4, R2, R3
On a single bus, moving R2, then R3, then the result takes several clocks. On a three-bus datapath, how many?
One. R2 on Bus A, R3 on Bus B, ALU adds, result on Bus C into R4 — all in a single step. More buses = fewer clocks per instruction, at the cost of more wiring.
🧠
Get this into your memory
Single- vs multiple-bus organization.
  • Single-bus — one shared path; one transfer per clock; cheap but slow (bottleneck).
  • Three-bus — Bus A + Bus B feed the ALU together; Bus C returns the result.
  • Effect — a register-to-register operation drops from several clocks to one.
  • Trade-off — more buses mean more hardware and wiring.
🔑
More buses buy fewer clocks — you trade wires for speed.
But single or triple, the datapath is just idle wires and an ALU. Something must raise the right signals, in the right order, every clock.

Control Unit

The datapath can move and compute — but it just sits there until someone raises the load lines, opens the buses, sets the ALU. Who conducts this orchestra?

Core

The control unit's one job

Each clock, raise the exact control signals the current step needs.

Inputs

the IR (which instruction), a step counter (which beat), and condition flags (Z, N, C, V).

Outputs

the control points: register loads, bus enables, ALU function, memory read/write.

Two ways to build it: hardwired or microprogrammed.

Core

Hardwired — signals from logic gates

A fixed circuit maps (IR + step + flags) straight to signals. Fast, but changing the instruction set means re-wiring the hardware.

Core

Microprogrammed — signals stored in memory

Each step is a microinstruction = control word (the signals) + sequencing word (the next address). The μPC walks through a microroutine in the control store.

Core

How the μPC picks the next microinstruction

In-line

increment the control address register (CAR).

Branch

unconditional or conditional (test Z, N, C, V).

Map

the instruction's opcode maps to its microroutine's start address.

So a machine instruction is executed by running a small microprogram — fetch routine, then the routine its opcode maps to.

?
Weigh them up
You need to add a new instruction after the chip is designed. Which control style makes that easy — and what do you pay?
Microprogrammed: just edit the control store (rewrite microcode) — flexible, but slower (an extra memory read per step). Hardwired is faster but rigid — a new instruction means redesigning the logic.
🧠
Get this into your memory
Control unit — hardwired vs microprogrammed.
  • Control unit — turns (IR + step + flags) into control signals each clock.
  • Hardwired — combinational logic + step counter; fast, rigid.
  • Microprogrammed — microinstructions in a control store; a μPC/CAR sequences them.
  • Microinstruction = control word (signals) + sequencing word (next address).
  • Sequencing — increment, branch, conditional branch, opcode mapping.
🔑
Control is just: which signals, in which order.
Wire that decision into gates, or store it as a microprogram — either way, it's what turns a datapath into a processor.
