Memory Hierarchy
If one memory could be fast, huge and cheap all at once, this whole chapter would not exist. Why can't it?
Notes Ch.1 · Foothold 4.1 · Hamacher §8.5 / Mano §12-1
1 · Memory Hierarchy

Why not one big, fast memory?

The gap · Before we name any solution, feel the problem: pick one memory technology for the whole machine and something always breaks.
Build it all from register-speed memory → blazing fast, but so costly per byte that an affordable machine holds barely one photo. Tiny.
Build it all from disk-speed memory → petabytes for pocket change, but the CPU (nanoseconds) idles for milliseconds on every fetch. CPU starves.
The real answer: a little very-fast memory close to the CPU, backed by progressively bigger, cheaper, slower memory further away — a hierarchy.
1 · Memory Hierarchy

The pyramid — four levels, one job each

What we want · The CPU checks the fastest, smallest level first; only on a miss does it step down to a bigger, slower one. Watch it build.
1 · Memory Hierarchy
🎤 Ask the class
Your program is running a loop. Where does the loop counter i live right now — and where do last year's holiday photos live?
i is touched every few nanoseconds → pulled up to a register. Old photos are opened maybe once a year → they sit on auxiliary storage. Nobody wrote code to place them — the hardware and OS move data up the pyramid by how hot it is.
1 · Memory Hierarchy

Locality of reference — why it actually works

Why now · A small fast level only helps if the next access is usually already in it. It is — because real programs don't scatter their accesses randomly.
Temporal locality: a just-used address (sum) is used again soon.
Spatial locality: an address next to a just-used one (arr[1] after arr[0]) is used soon too.
🔑 Key insight
The hierarchy is an illusion of memory that is both large and fast — bought by keeping the fast part small.
And it only pays off because of locality: a small cache of "recently touched" data captures most of the traffic.

Main Memory — RAM & ROM Chips
The pyramid called it "Main Memory (RAM)". Now we open that box — what is inside a memory chip, and how is it wired?
Notes Ch.2 · Foothold 4.2 · Hamacher §8.1–8.3 / Mano §12-2
2 · Main Memory

Opening the box — memory as real hardware

Recall · In Unit 1 memory was a wall of numbered lockers: give an address, get a byte. True from outside — but a real chip must do that with wires and transistors.
  • You supply an address on the address lines and a read/write command…
  • …the chip must physically select exactly one location out of thousands…
  • …and move that location's bits out (read) or in (write) on the data lines.
  • Inside the "black box": a decoder + a grid of storage cells. Let's build one.
2 · Main Memory

Chip anatomy — an 8-word × 4-bit RAM

Build it · A shrunk-down chip so every wire fits on screen. Three address lines, one decoder, a cell grid, control and data lines — revealed one part at a time.
2 · Main Memory
🎤 Ask the class
We put A₂A₁A₀ = 011 on the address lines. Which word line does the 3→8 decoder assert — and how many bits come out?
Binary 011 = word 3 — the decoder raises exactly one of its 8 outputs. All 4 bits of that word appear on D3–D0 together. n address lines always select one of 2ⁿ locations; add data lines, not address lines, to widen each word.
2 · Main Memory

RAM comes in two flavours: SRAM vs DRAM

A contrast · Both give random access in equal time, but they store a bit in completely different ways — and that difference decides where each is used.
The whole reason main memory is DRAM: 1 transistor per cell packs far more bits for far less cost — refresh is the price.
2 · Main Memory

The ROM family — one story, five variants

Where this fits · ROM is non-volatile — it survives power loss. "Read-only" softened over the decades: each generation made ROM easier to rewrite.
2 · Main Memory

Building a larger module from small chips

The payoff · No single chip is big enough for a real machine. Combine many small chips two ways — and the memory address map falls right out.
🔑 Key insight
A memory module is just a decoder + a grid of cells, scaled up: stack chips to widen the word, line them up to extend the address range.
RAM (SRAM/DRAM) is volatile working memory; ROM is non-volatile — and the address map is simply "high bits pick the chip, low bits pick the word."
3
Auxiliary Memory
The pyramid's base was labelled "non-volatile". Pull the power on a RAM-only machine — what is left?
Notes Ch.3 · Foothold 4.5 · Hamacher §8.9–8.11 / Mano §12-3
3 · Auxiliary Memory

Why auxiliary storage has to exist

The gap · Main memory (DRAM) is fast enough — but it is volatile. The moment power is lost, every stored charge disappears.
  • A machine built only from RAM works fine — until you switch it off. Then it has nothing left.
  • Auxiliary (secondary) memory is the opposite of RAM on the one axis that matters for permanence: non-volatile.
  • The trade: your data survives power loss, at the cost of being far slower to access (milliseconds, not nanoseconds).
  • It also lives outside the CPU–cache–main-memory core, reached through the I/O system — magnetic disks, tape, optical.
3 · Auxiliary Memory

Magnetic disk — the anatomy

What we want · Before timing a read, name the parts. A disk stores bits magnetically on concentric rings, addressed by track and sector.
3 · Auxiliary Memory

Trace a read — three waits, back to back

Build it · Request: read sector 47 on track 12. One disk access hides two completely different kinds of waiting — watch the platter spin under a barely-moving head.
① Seek — the arm moves radially to track 12. (mechanical — the slow part)
② Rotational wait — head is on track 12, but sector 47 hasn't rotated under it yet.
③ Transfer — bits stream off the track as it spins under the stationary head.
Taccess = Tseek + ½ rotation + Ttransfer
Rotational latency is an average — the sector could be under the head already (0) or need a full spin (worst); half a revolution is the expected wait.
3 · Auxiliary Memory
🎤 Ask the class
The head just reached track 12 — but sector 47 just passed by. How long until it comes back around: best case, worst case, average?
Best ≈ 0 (it's already there next time), worst ≈ one full revolution, average ≈ ½ revolution. That ½-rotation is the rotational latency term — a statistical average, not a fixed number.
3 · Auxiliary Memory

Comparing the media

Where this fits · Not all auxiliary storage works the same way. The big divide: random access vs sequential access.
🔑 Key insight
Auxiliary memory buys permanence — non-volatile, huge, cheap — by giving up speed.
Disk access = Tseek + ½ rotation + Ttransfer; tape trades away random access entirely for the lowest cost per byte of all.

Associative Memory
Every memory so far was found by its address. What if you know only what you're looking for — not where it is?
Notes Ch.4 · Foothold 4.4 · Mano §12-4 (Hamacher has no dedicated section)
4 · Associative Memory

Search by content, not by address

The gap · Ordinary RAM answers "what is at address A?" But often we ask the reverse: "which location holds this value?" — and we don't know the address.
  • Address-by-address search means checking locations one at a time — slow when the table is large.
  • An associative memory (a.k.a. content-addressable memory, CAM) compares every word to the search value simultaneously, in parallel.
  • The parallel-comparison hardware costs more per bit — so it's reserved for cases where search time is critical (e.g. a fully-associative cache tag check, or the TLB in Ch.7).
4 · Associative Memory

Anatomy — four registers, no address input

Build it · Notice as it appears: there is no address line anywhere. You supply content and get back which words matched.
4 · Associative Memory

Masked compare — the key decides what counts

A doubt to settle · Why a Key register at all? Because we often want to match only part of a word. The notes' worked example: compare just the first three bits.
4 · Associative Memory
🎤 Ask the class
With A = 101 101101 and K = 111 000000, a word reads 101 000000. Match or no match? And how many words could match at once?
Match — its first three bits are 101, and nothing else is compared. And any number of words can match simultaneously — every word whose first 3 bits are 101 sets its M-bit to 1. That's the power (and cost) of parallel content search.
4 · Associative Memory

Reading, writing, and the tag bit

Recall · There's no address to write to. So how do we add or delete a word? A single extra tag bit per word tracks "in use / free".
  • Read: supply content in A (and mask K); the matching words announce themselves through M. No address ever named.
  • Write (add): the new word lands in the first location whose tag bit is 0 (free) — the tag then flips to 1 (in use).
  • Delete: just clear the tag to 0. The bits are still physically there — the location is simply marked unused and free to overwrite.
🔑 Key insight
Associative memory is accessed by content, not address — every word compared in parallel, the key masking which bits count.
Parallel hardware is costly per bit, so it's used only where search speed is critical — remember this: the TLB in Chapter 7 is an associative memory.

Cache Memory
Chapter 1 told us WHY a small fast cache works (locality). Now the hardware question: when a block arrives, WHERE in the cache does it go?
Notes Ch.5 · Foothold 4.3 · Hamacher §8.6 / Mano §12-5
5 · Cache Memory

The placement problem

Where this fits · Main memory has hundreds of thousands of blocks; the cache holds only a handful of lines. So two questions must be answered by hardware, fast.
  • When block N is fetched from main memory, which cache line does it go into?
  • Later, to check if block N is already cached, which line(s) must we compare — and how few can we get away with?
  • Three answers, trading flexibility against how much comparison hardware a lookup needs.
5 · Cache Memory

Three mapping techniques — same block, three rules

A contrast · Follow one main-memory block and watch where it is allowed to land under each scheme.
5 · Cache Memory

Where it lands — splitting the address

Build it · Worked example used all through this topic: a 512-line cache, 16 words per line, main memory reached by a 24-bit address. Only the middle field changes across schemes.
5 · Cache Memory
🎤 Ask the class
A tiny 4-line direct-mapped cache (line = block mod 4). Block 0 is sitting in line 0. Now block 4 is referenced. What happens — and why is it avoidable waste?
4 mod 4 = 0, so block 4 is forced into line 0 and evicts block 0 — even if lines 1, 2, 3 sit empty. Blocks 4 apart always fight over the same line. This exact weakness is what fully-associative and set-associative mapping exist to reduce.
5 · Cache Memory

Two more decisions: replace, and write

Why now · Once a set can hold several blocks, two policies remain: when the set is full, who leaves? And when the CPU writes, when does main memory learn?
  • FIFO evicts the oldest arrival; LRU evicts the least-recently-used. Same access stream → they can evict different lines.
  • Write-through: every write updates cache and main memory at once — always consistent, more traffic.
  • Write-back: write updates only the cache (marked dirty); main memory is updated later, when the line is evicted — far less traffic, small risk.
🔑 Key insight
Same block, three rules: direct = one slot (cheap, collides), fully associative = anywhere (flexible, costly search), set-associative = the middle ground nearly every real cache uses.
Layered on top: a replacement policy (LRU/FIFO) and a write policy (write-through/write-back).
6
Virtual Memory
Physical RAM is fixed and small. Yet programs — many at once — act as if they each own a huge private memory. How?
Notes Ch.6 · Foothold 4.6 · Hamacher §8.8 / Mano §12-6
6 · Virtual Memory

Bigger than RAM — the illusion

What we want · Let a program's address space be larger than physical memory, and let many programs coexist — without any of them knowing where they really sit.
  • Every program is given the illusion of a large, private address space (its virtual/logical addresses).
  • Only the actively-used pieces are kept in physical RAM; the rest waits on auxiliary storage (Ch.3) until needed.
  • Hardware + OS translate each virtual address to a real physical one on every reference — invisibly.
6 · Virtual Memory

Pages, blocks, and the page table

Build it · Both spaces are chopped into equal-size pieces — the address space into pages, physical memory into blocks/frames — so any page fits any block.
6 · Virtual Memory

Translation — every reference takes one of three paths

A contrast · A small associative cache of recent translations — the TLB — sits in front of the page table. What happens next depends on what it, and the page table, know.
6 · Virtual Memory
🎤 Ask the class
A reference misses the TLB, so we walk the page table — and its present bit is 0. What must happen now, and why is it so much slower than a cache miss?
It's a page fault: the page isn't in RAM, so the OS fetches it from disk (auxiliary memory) into a free block, updates the page table, and restarts the reference. A cache miss costs a main-memory fetch (~100 ns); a page fault costs a disk fetch (~milliseconds) — tens of thousands of times slower. LRU (Ch.5) picks which resident page to evict if RAM is full.
6 · Virtual Memory

Mano's associative-memory page table

Recall · A page table needs one entry per page — huge and mostly empty, since only a few pages are resident. Mano's fix reuses Chapter 4 directly.
  • Store the page table itself as an associative memory, sized to the number of blocks (few), not pages (many).
  • Each word holds a (page number, block number) pair. Present the page number as the argument…
  • …a match returns the block number directly; no match means a page fault. This is the idea behind the TLB you'll meet in Chapter 7.
🔑 Key insight
Virtual memory gives every program a large private space, keeping only the active pages in RAM and the rest on disk.
A page fault is a disk fetch — far costlier than a cache miss — and the same LRU logic from cache decides which page is evicted.

Memory Management Hardware
Nothing new to invent here — this chapter combines six chapters' ideas into one working translation from logical to physical address.
Notes Ch.7 · Foothold 4.C · Mano §12-7 (Hamacher: brief MMU/TLB mention)
7 · Memory Management Hardware

The MMU's mission — logical → physical

Where this fits · Programs speak in logical addresses; RAM answers only to physical ones. The Memory Management Unit translates every access, in hardware, on the fly.
  • Modern systems combine two ideas: segmentation (logical, variable-size regions — code, stack, data) and paging (fixed-size pieces that fit RAM blocks).
  • A segmented-page logical address has three parts: segment · page · word (offset).
  • The MMU must turn that into a real block + offset — and do it fast enough to sit on every single memory reference.
7 · Memory Management Hardware

Segmented-page mapping — the two-level walk

Build it · Version 1, no shortcuts: two table lookups turn the logical address into a physical one.
7 · Memory Management Hardware

The TLB fast path — a worked example in hex

The payoff · Put a small associative memory (the TLB — Chapter 4!) in front of the two tables, caching recent (segment, page) → block results. Locality (Ch.1) makes it pay.
7 · Memory Management Hardware
🎤 Ask the class
Now translate Seg 6 / Page 0 / Word 10 — and it's not in the TLB. Walk it. What are the steps, and what happens at the end?
TLB miss → ① index the segment table with seg 6 to get the page-table base → ② index that page table with page 0 to get the block → ③ combine block + word 10 → physical address → ④ cache the (6, 0) → block result in the TLB, so next time it's a hit. Six steps instead of four — two of them the table lookups the TLB is built to skip.
7 · Memory Management Hardware

Memory protection — the segment descriptor

Why now · Translating an address is only half the job. The same tables let the MMU validate every access — one program must not read or wreck another's memory.
Every access is both translated and checked — out of bounds or wrong permission → the hardware raises a fault.
🔑 Key insight
The TLB is itself an associative memory (Chapter 4) — searching by (segment, page) content to skip the slow two-table walk.
Memory management = translate and protect: base + length + permission on every reference, with the TLB making the common case fast.
Unit 4 · wrap-up

One system, built layer by layer

The payoff · Every topic in this unit was one layer of a single machine. Here is how they lock together on one memory reference.
  • Hierarchy + locality told us why a fast path matters (Ch.1).
  • RAM/ROM chips are the physical main memory being addressed (Ch.2); auxiliary memory is what a page fault falls back to (Ch.3).
  • Associative memory gave us the TLB's hardware (Ch.4); cache gave us the mapping + replacement policies (Ch.5).
  • Virtual memory gave us pages and the page table (Ch.6); the MMU walks segment → page → block and validates it (Ch.7).
  • From one register to a full address translation — you've built the entire memory system.
