1. Accessing I/O Devices

Hamacher §3.1 (Accessing I/O Devices, I/O Device Interface, Program-Controlled I/O)

1.1 The interconnection network and the two ways to reach a device

  • The processor, the memory, and the I/O devices are all tied together by an interconnection network (a bus, in the simplest case) — the shared set of wires over which every transfer of information travels.
  • For the processor to talk to a device, the device must look like a set of addressable locations, exactly as memory does. There are two schemes for assigning those addresses:
    • Memory-mapped I/O — some addresses in the processor's normal address space are set aside for I/O registers instead of memory. Because the device shares the memory address space, any instruction that can access memory (Load, Store, Move) can also access a device. This is the scheme used in most computers, and the one Hamacher follows.
    • Isolated (port-mapped) I/O — I/O has a separate address space, reached only by special In/Out instructions. It keeps the memory map free but needs extra instructions and a control line to say "this address is an I/O port, not memory."
Key idea: memory-mapped I/O means a device register such as DATAIN is read simply with Load R2, DATAIN and written with Store R2, DATAOUT — the same instructions used for memory. No special I/O instruction set is required.
Figure 3.1 — A computer system (Hamacher §3.1). The processor, memory, and I/O devices all communicate over one shared interconnection network.

1.2 The I/O device interface — data, status, control registers

  • A device does not connect to the bus directly; it connects through a device interface circuit. The interface holds a small set of addressable registers, of three kinds:
    • a data register — a buffer that holds the byte/word being transferred (e.g. KBD_DATA, DISP_DATA);
    • a status register — flags that report the device's current condition (e.g. KIN = "a key has been pressed", DOUT = "display is ready for the next character");
    • a control register — bits the processor writes to govern how the device behaves (e.g. an interrupt-enable bit).
  • To the programmer these registers simply look like memory locations at fixed addresses. In Hamacher's example the keyboard's data register sits at 0x4000, its status register at 0x4004 (four bytes higher) and its control register at 0x4008 — word-aligned in a 32-bit machine.
Figure 3.2 — The connection for processor, keyboard and display (Hamacher §3.1.1). Each device hangs off the interconnection network through an interface that exposes DATA, STATUS and CONTROL registers to the processor.
Figure 3.3 — Registers in the keyboard and display interfaces (Hamacher §3.1.2). Only the bits used for I/O are labelled: KIN/DOUT (ready flags), KIRQ/DIRQ (interrupt-pending flags) and KIE/DIE (interrupt-enable control bits).

1.3 Program-controlled I/O (polling)

  • The simplest way to transfer data is program-controlled I/O: the processor itself runs a loop that repeatedly reads a status flag and moves one byte when the flag says the device is ready. Reading a status flag to see whether the device is ready is called polling.
  • The synchronization problem this solves is a speed mismatch: a keyboard delivers a few characters per second, a display a few thousand, but a processor executes billions of instructions per second. The status flag is the handshake that keeps the fast processor from running ahead of the slow device.
  • A read of one character is written as a wait loop:
    • READWAIT:  LoadByte R4, KBD_STATUS
    •            And R4, R4, #2  ← test the KIN bit (bit 1)
    •            Branch_if_[R4]=0 READWAIT  ← still not ready, keep looping
    •            LoadByte R5, KBD_DATA  ← ready: read the character
  • The big drawback: while it spins in that loop the processor does no useful work. This wasted "busy-waiting" is precisely the problem that interrupts (Chapter 2 below) and DMA (Chapter 4) are designed to remove.
WORKED EXAMPLE

Q. A keyboard delivers at most 10 characters per second. A processor runs a polling loop that tests the KIN flag; the loop body (load-status, AND, branch) takes 3 instructions of 1 ns each, i.e. 3 ns per poll. Roughly how many times does the processor poll the status flag between two consecutive keystrokes, and what does this tell you about program-controlled I/O?

A. Time between keystrokes = 1 / 10 = 0.1 s = 108 ns. Each poll costs 3 ns, so the number of polls ≈ 108 / 3 ≈ 33 million polls per character. Almost the entire processor's time is spent asking "are you ready yet?" — a vivid demonstration of why busy-wait polling is wasteful, and why we move to interrupt-driven I/O.

2. Interrupts

Hamacher §3.2, §3.2.1 (Enabling/Disabling), §3.2.2 (Handling Multiple Devices), §3.2.4 (Control Registers)

2.1 The idea: let the device call the processor

  • Instead of the processor polling, we let the device send a hardware signal — an interrupt request (IRQ) — when it becomes ready. The processor gets on with useful work and responds only when the signal actually arrives. Ideally the busy-wait time disappears entirely.
  • When a request is accepted, the processor suspends the program it is running and executes a special routine called the interrupt-service routine (ISR). When the ISR finishes, a Return-from-interrupt instruction resumes the interrupted program exactly where it left off.
  • An interrupt resembles a subroutine call, but with one crucial difference: a subroutine is called deliberately by the program and is related to it; an ISR is triggered by an external, unrelated event and may touch registers the interrupted program was using. Therefore the processor must save and later restore the machine state (at minimum the program counter and the processor status register, PS).
Figure 3.6 — Transfer of control through the use of interrupts (Hamacher §3.2). An interrupt arriving during instruction i of the COMPUTE routine causes control to jump to the DISPLAY (service) routine; on return, execution resumes at instruction i+1.
Key term — interrupt latency: the delay between the arrival of an interrupt request and the start of the ISR. Because saving registers costs memory writes, processors save only the minimum state automatically (PC and PS); anything else is saved by explicit instructions at the top of the ISR. Some machines instead use shadow registers (a duplicate register set for the ISR) to avoid saving/restoring altogether.

2.2 Interrupt hardware and acknowledgement

  • A device requests an interrupt by activating a request line; it keeps that line active until it learns the processor has accepted the request. The processor tells the device its request has been seen either by a dedicated interrupt-acknowledge signal, or implicitly — the ISR accessing the device's data/status register serves as the acknowledgement, after which the device drops its request.
  • When several devices share one interrupt line, each connects to it through an open-collector (or open-drain) gate so that the common line is asserted if any device requests service — effectively a wired-OR of all the individual request signals.

2.3 Enabling and disabling interrupts

  • Because interrupts arrive at unpredictable times, the programmer must be able to switch them on and off. Control exists at two ends:
    • At the processor: a single interrupt-enable bit (IE) in the PS register. IE = 1 ⇒ requests are accepted; IE = 0 ⇒ all requests are ignored.
    • At the device: an interrupt-enable bit in the device's control register (e.g. KIE). The device may raise a request only when this bit is set.
  • A subtle danger: the request line stays active during the ISR, which could immediately re-interrupt and cause an infinite loop. The standard cure: on accepting an interrupt the processor automatically clears IE (disabling further interrupts) after saving the PS; the Return-from-interrupt restores the saved PS, setting IE back to 1.
  • Typical single-device sequence: (1) device raises IRQ; (2) processor saves PC and PS; (3) IE is cleared to disable further interrupts; (4) the ISR runs and the device is told its request is recognised, so it deactivates IRQ; (5) the saved PC and PS are restored (re-enabling interrupts) and the interrupted program resumes.
Figure 3.7 — Control registers in the processor (Hamacher §3.2.4). Besides the status register PS (holding IE), a copy IPS preserves the old PS during an interrupt; IENABLE selects which devices may interrupt, and IPENDING shows which are currently requesting.

2.4 Handling multiple devices

  • With many independent devices, four questions must be answered: which device interrupted, where is its service routine, may a device interrupt while another ISR runs, and how are simultaneous requests resolved? Two mechanisms answer the first two:
    • Polling (software identification): on an interrupt the ISR reads the IRQ bit of each device's status register in turn; the first device found with its bit set is serviced. Simple, but slow — time is wasted checking devices that are not requesting.
    • Vectored interrupts: the requesting device identifies itself directly by sending a code (a vector) to the processor. That code indexes an interrupt-vector table in low memory holding the starting address of each device's ISR; the address is loaded straight into the PC. No polling — the correct routine is entered immediately.
  • Interrupt nesting & priority: normally interrupts stay disabled inside an ISR so a routine runs to completion. But an urgent device (e.g. a real-time clock) may need to interrupt during another device's ISR. So devices are given priority levels: the processor runs at the priority of the current routine and accepts a request only from a device of higher priority — lower- or equal-priority requests remain blocked. This lets high-priority interrupts nest inside lower-priority ones.
  • Daisy chaining: a common hardware way to resolve simultaneous requests without individual lines. Devices share one request line and are connected in a chain along the acknowledge line; the acknowledge signal ripples device-to-device, and the first device in the chain that has a pending request grabs it and blocks the signal from passing further. Position in the chain therefore fixes priority.
WORKED EXAMPLE

Q. (Hamacher, adapted from Problem 7.3) A processor has seven interrupt-request lines, INTR1 to INTR7. INTR7 has the highest priority and INTR1 the lowest. Suppose device on INTR4 is currently being serviced when requests arrive on INTR2, INTR5 and INTR6. In what order are the three new requests serviced?

A. While the INTR4 routine runs, the processor's priority is 4, so it accepts only requests above 4. Thus INTR2 is blocked for now; INTR5 and INTR6 are accepted, and of those the higher-priority INTR6 is taken first, nesting inside it INTR5 only if a still-higher request came — here INTR6, then INTR5. When the processor finally drops back below priority 2, the pending INTR2 is serviced last. Order: INTR6 → INTR5 → (finish INTR4) → INTR2.

3. Exceptions & Interrupts in the Operating System

Hamacher §3.2.6 (Exceptions) · §3.2.5 and general use of interrupts by the OS

3.1 What an exception is

  • The interrupt mechanism is not only for I/O. In general, an exception is any event that causes an unscheduled transfer of control — the interrupt hardware is reused to jump to a handler routine. I/O interrupts are just one kind of exception.
  • The main categories of exception:
    • I/O interrupts — a device signalling that it is ready or that a transfer is complete (the case in Chapter 2).
    • Error / hardware faults — conditions detected during execution, such as division by zero, arithmetic overflow, an illegal opcode, or a memory-parity error. Control passes to a handler that reports the error or attempts recovery; the offending instruction may be re-tried or the program aborted.
    • Debugging support — exceptions let a debugger stop a program: a trace exception occurs after every instruction (single-stepping), and a breakpoint exception occurs when execution reaches a marked instruction.
    • Privilege / operating-system requests — a user program uses a special instruction (a software interrupt or system call) to request an OS service; this is deliberately triggered but uses the same exception machinery.
Key distinction: an interrupt usually means an external, asynchronous event (an I/O device), whereas an internally-generated exception/trap is synchronous — caused by the instruction currently executing (overflow, page fault, system call). Both are handled through the same save-state / vector / return mechanism.

3.2 How the operating system uses interrupts

  • Multitasking & the timer interrupt: a periodic hardware timer raises an interrupt at fixed intervals. Its ISR is the operating system's chance to run the scheduler, which may suspend the current program and switch the processor to another — this is how time-sharing / pre-emptive multitasking is implemented. Without the timer interrupt a runaway program could never be pre-empted.
  • System calls: a user program cannot touch devices directly (that is a privileged operation). To read a file or print, it executes a software-interrupt instruction that traps into the OS; the OS performs the operation on the program's behalf and returns. This protects devices and enforces controlled sharing.
  • Two privilege levels: the processor runs either in user (unprivileged) mode or supervisor (privileged) mode. Interrupt/exception handling switches the processor into supervisor mode so the OS can execute privileged instructions; the Return-from-interrupt drops it back to user mode. A user program attempting a privileged instruction itself causes an exception.
  • Device management: the actual device drivers live inside the OS as interrupt-service routines. When a device finishes, its I/O interrupt wakes the driver, which moves data and possibly unblocks the waiting user process. Thus interrupts are the glue between hardware events and the scheduler.
WORKED EXAMPLE

Q. A time-sharing system gives each program a 10 ms time-slice using a timer interrupt. The timer ISR (save context, run scheduler, restore context) takes 20 μs. What percentage of processor time is spent on scheduling overhead, and what happens to that percentage if the slice is shortened to 1 ms for snappier response?

A. With a 10 ms slice: overhead = 20 μs / (10 ms + 20 μs) ≈ 20 / 10020 ≈ 0.2% — negligible. With a 1 ms slice: 20 μs / 1020 μs ≈ 1.96%. Shorter slices give more responsive multitasking but spend a larger fraction of the CPU on the scheduling interrupt — the classic responsiveness-vs-overhead trade-off the timer interrupt exposes.

4. Direct Memory Access & Bus Arbitration

Hamacher §8.4 (Direct Memory Access) · §7.3 (Arbitration)

4.1 Why DMA?

  • Both polling and interrupt-driven I/O move data one word at a time through the processor: every word costs several instructions and, with interrupts, the overhead of saving/restoring state. For a block transfer of thousands of words to or from a disk or network card, that per-word overhead is intolerable.
  • Direct Memory Access (DMA) lets a special control unit — the DMA controller — move a whole block directly between main memory and the device, without the processor handling each word. For every word it supplies the memory address and control signals, increments the address, and counts down the words remaining — the jobs the processor would otherwise do.
  • The processor is involved only twice: once to start the transfer, and once at the end when the controller raises a single interrupt to say the block is done.

4.2 The DMA controller's registers

  • To start a transfer, an OS routine writes three things into the DMA controller: the starting address in memory, the word count (block length), and the direction of transfer.
  • Hamacher's example (Figure 8.12) uses three registers:
    • Starting address register — where in memory the block begins;
    • Word count register — how many words to transfer;
    • Status and control register — holds the direction bit R/W̄ (1 = read from memory to device, 0 = write to memory), the Done flag (set when the block is finished), the IE interrupt-enable bit, and the IRQ bit (set when the controller raises its completion interrupt).
Figure 8.12 — Typical registers in a DMA controller (Hamacher §8.4). The R/W̄ bit sets the direction; Done, IE and IRQ in the status/control word manage the completion interrupt.

4.3 DMA in the system, and cycle stealing vs burst mode

  • A DMA controller may be built into a device interface (as with a disk controller offering several DMA channels, one per disk) or be a separate unit shared by several devices. It sits on the I/O bus alongside the processor and memory.
  • Since both the processor and the DMA controller need the memory bus, their accesses must be interleaved. Two styles:
    • Cycle stealing — the controller "steals" occasional bus cycles from the processor, one (or a few) words at a time. The processor is only briefly delayed and keeps running between steals. This is the most common mode.
    • Burst (block) mode — the controller keeps the bus for the whole block, transferring at full speed while the processor waits. Faster for the transfer, but it stalls the processor for the duration.
  • Because the DMA controller and the processor contend for the single memory bus, DMA makes bus arbitration essential (next section). A bus master is any unit that can initiate a transfer; the processor is normally the master, but a DMA controller must become master to drive the bus during its transfer.
Figure 8.13 — Use of DMA controllers in a computer system (Hamacher §8.4). One DMA controller serves a high-speed Ethernet; a disk controller with its own DMA capability provides two channels, one per disk.

4.4 Bus arbitration

  • When more than one unit can be a bus master (processor, DMA controllers), only one may drive the bus at a time. Bus arbitration is the process of deciding which requesting master is granted the bus, performed by an arbiter circuit that associates a priority with each request. Two organisations:
    • Centralized arbitration — a single arbiter (often inside the processor) receives all Bus-Request lines and returns Bus-Grant lines. A master raises its Bus-Request (BR); the arbiter answers with a Bus-Grant (BG); the master uses the bus and, when done, drops BR, whereupon the arbiter drops BG. If several request at once the higher-priority master is granted first; with no urgency, a fair round-robin scheme can be used.
    • Distributed arbitration — there is no central arbiter; every master carries an ID and participates in deciding the winner (by driving a shared set of arbitration lines and comparing), so the highest-priority requester wins collectively.
  • Arbitration must guarantee fairness — no master is starved indefinitely — while still letting time-critical devices win when needed.
Figure 7.8 — Bus arbitration (Hamacher §7.3). Each master has a Bus-Request (BR) and a Bus-Grant (BG) line to the central arbiter.
Figure 7.9 — Granting use of the bus based on priorities (Hamacher §7.3). Master 1 has highest priority: even though master 3 requests before master 1, the arbiter grants the bus to master 1 first.
WORKED EXAMPLE

Q. A disk transfers a 4 KB block (1024 words of 32 bits) to memory by DMA. Each word transfer uses one memory bus cycle of 10 ns. (a) How long does the block transfer take? (b) Under cycle stealing, if the processor otherwise issues a memory access every 40 ns, by roughly what percentage is the processor slowed during the transfer?

A. (a) 1024 words × 10 ns = 10.24 μs of bus time. (b) The DMA needs the bus for 1024 cycles over the transfer. In each 40 ns window the processor wants 1 cycle and DMA steals 1 cycle, so the processor sees roughly 1 stolen cycle (10 ns) of delay per 40 ns → about a 25% slowdown while the transfer is in progress — and note the processor is only interrupted once, at completion, instead of 1024 times as interrupt-driven I/O would require.

5. Synchronous vs Asynchronous Buses

Hamacher §7.2.1 (Synchronous Bus) · §7.2.2 (Asynchronous Bus)

5.1 The bus and its protocol

  • A bus is the shared set of lines — address, data and control — joining the units of a computer. The rules that say when a device may drive the bus and when it may sample it are the bus protocol, enforced by control signals such as the R/W̄ line.
  • In any transfer one unit is the master (it issues the Read/Write command — usually the processor or a DMA controller) and the addressed unit is the slave. Timing of transfers is classified as either synchronous or asynchronous.
  • Only one device may drive a shared line at a time; this is achieved with tri-state gates (bus drivers), which either drive a 0/1 or go into a high-impedance state that leaves the bus undisturbed.

5.2 Synchronous bus

  • On a synchronous bus every device takes its timing from a common bus clock. A transfer happens within a fixed number of clock cycles agreed in advance.
  • Simple Read (one clock cycle, Figure 7.3): at t0 the master puts the address and command on the bus; by t1 the addressed slave has decoded them and placed the data on the data lines; at t2 (end of the cycle) the master latches the data into a register. The clock period must be long enough for the slowest device and the worst-case propagation delay.
  • Two limitations of the one-cycle scheme: it forces every device to run at the speed of the slowest, and the master has no confirmation that the slave actually responded (a faulty device is undetected).
  • Multiple-cycle transfer (Figure 7.5) fixes both: the slave asserts a Slave-ready signal when its data is on the bus, so a transfer may span as many cycles as the device needs, and a missing Slave-ready (after a timeout) flags a failed transfer.
Figure 7.3 — Timing of an input transfer on a synchronous bus (Hamacher §7.2.1). Address/command are placed at t0; the slave's data appears by t1; the master latches it at t2.
Figure 7.5 — An input transfer using multiple clock cycles (Hamacher §7.2.1). The Slave-ready acknowledgement lets a slow device take extra cycles and lets the master detect a non-responding device.

5.3 Asynchronous bus

  • An asynchronous bus uses no clock at all. Instead the master and slave coordinate with a handshake — an interlocked exchange of two control signals, Master-ready and Slave-ready.
  • Input transfer (Figure 7.6): the master puts address and command on the bus (t0), then raises Master-ready (t1); the addressed slave decodes, places its data and raises Slave-ready (t2); the master receives Slave-ready, latches the data and drops Master-ready (t3); it removes the address (t4); the slave then removes data and Slave-ready (t5). Every edge on one signal is a response to an edge on the other — a full handshake.
  • The gap t1 − t0 allows for bus skew (different lines propagating at slightly different speeds) so Master-ready never arrives ahead of the address it announces.
Figure 7.6 — Handshake control of data transfer during an input operation (Hamacher §7.2.2). The fully-interlocked Master-ready / Slave-ready exchange makes the transfer self-timed.
Figure 7.7 — Handshake control of data transfer during an output operation (Hamacher §7.2.2). The master supplies the data with the address; the slave loads it when Master-ready is asserted and replies with Slave-ready.

5.4 Synchronous vs asynchronous — the trade-off

Synchronous: simple, and fast — the clock period need cover only one round-trip delay, so high transfer rates are achievable; slow devices are handled by adding clock cycles. But the clock must be distributed carefully and delays kept within strict bounds. Asynchronous: no shared clock to distribute, so delays of any device are absorbed automatically and timing design is simpler and very flexible. But each transfer needs two round trips (four end-to-end delays) of handshaking, so it is inherently slower. Most modern high-speed buses are synchronous.
WORKED EXAMPLE

Q. A synchronous bus has a clock period of 5 ns and transfers one 32-bit word per bus cycle (single-cycle transfer). (a) What is the maximum data-transfer rate in bytes/second? (b) If devices instead need 4 clock cycles per word, what is the rate?

A. (a) One word (4 bytes) every 5 ns → rate = 4 bytes / 5 ns = 0.8 bytes/ns = 800 MB/s. (b) 4 cycles = 20 ns per word → 4 bytes / 20 ns = 200 MB/s. The extra cycles that let slow devices participate cut the peak rate by the same factor — the price of accommodating the slowest slave on a synchronous bus.

6. Standard I/O Interfaces: PCI & SCSI

Hamacher §7.5.3 (PCI Bus) · §7.5.4 (SCSI Bus)

6.1 Why standard interfaces?

  • A computer's processor bus is specific to that processor. To let a wide variety of devices from many manufacturers plug in, the system provides one or more standard I/O interconnection standards — agreed electrical, signalling and mechanical specifications. A bridge circuit connects the processor bus to the standard I/O bus and translates transactions between them.

6.2 The PCI bus

  • PCI (Peripheral Component Interconnect) is a low-cost, processor-independent bus mounted on the motherboard for connecting I/O interfaces. A device on the PCI bus appears to the processor as if it were connected directly to the processor bus, with its registers mapped into the processor's address space.
  • The PCI bus connects to the processor bus through a bridge, which also has the port for main memory (and often a fast graphics port). The bridge relays commands and data between the two buses (Figure 7.18).
  • PCI is synchronous and supports burst (block) transfers: the address is sent once, then several consecutive data words are transferred back-to-back — ideal for the block transfers DMA performs. Its main signals are summarised in Table 7.1:
    • CLK — the 33- or 66-MHz bus clock;
    • FRAME# — asserted by the initiator (master) to mark the duration of a transaction;
    • AD — 32 (optionally 64) lines that carry the address and then the data, time-multiplexed on the same wires;
    • C/BE# — command / byte-enable lines;
    • IRDY#, TRDY# — Initiator-ready and Target-ready handshake signals;
    • DEVSEL# — asserted by the target (slave) to say it has recognised its address;
    • IDSEL# — used to select a device during initialization/configuration.
  • The two parties are called the initiator (master) and the target (slave). A Read (Figure 7.19): the initiator drives the address on AD and a command on C/BE# with FRAME# asserted; the target answers with DEVSEL#; then data words are handed over one per clock as long as both IRDY# and TRDY# are asserted, giving a burst of consecutive words.
Figure 7.18 — Use of a PCI bus in a computer system (Hamacher §7.5.3). The PCI bridge joins the processor bus, main memory and the PCI bus; device controllers (disk, Ethernet, USB) attach to the PCI bus.
Table 7.1 — Data-transfer signals on the PCI bus (Hamacher §7.5.3).
Figure 7.19 — A Read operation on the PCI bus (Hamacher §7.5.3). One address is sent on AD, then a burst of four data words (#1–#4) is read, paced by IRDY# and TRDY#.

6.3 The SCSI bus

  • SCSI (Small Computer System Interface) is a standard parallel bus for connecting storage and other peripherals (disks, tape, scanners). Devices attach to a shared cable in a daisy-chain; the standard defines 8-bit (narrow) and 16-bit (wide) data paths.
  • Every unit on the bus is either an initiator (usually a controller in the computer, which issues commands) or a target (the device that carries them out). Each device has a SCSI ID, and the bus is arbitrated so that only one initiator–target pair uses it at a time.
  • A SCSI transaction proceeds through a defined sequence of bus phases: Arbitration (a device wins control of the bus) → Selection (the initiator selects a target by its ID) → Command (the initiator sends the operation, e.g. read block N) → Data (the block is transferred) → Status / Message (the target reports completion). Between issuing the command and having the data ready, the target may disconnect from the bus (freeing it for others) and later reconnect — important because a disk seek is slow.
  • SCSI historically offered high performance and the ability to chain many devices on one controller; it has since been largely superseded by SAS (Serial Attached SCSI) and SATA for disks, but the initiator/target command model lives on.
PCI vs SCSI in one line: PCI is the system interconnect on the motherboard that carries every kind of device controller close to the processor; SCSI is a peripheral bus that hangs storage devices off one such controller. In Figure 7.18 the "SATA/SAS or SCSI controller" is itself a device on the PCI bus — the two standards work at different levels of the system.
WORKED EXAMPLE

Q. A 33-MHz, 32-bit PCI bus performs a burst Read. The first data word appears 2 clock cycles after FRAME# is asserted, and thereafter one 32-bit word is transferred per clock. How long does it take to read a burst of 8 words, and what is the effective transfer rate over that burst?

A. Clock period = 1 / 33 MHz ≈ 30 ns. Time = 2 setup cycles + 8 data cycles = 10 cycles × 30 ns = 300 ns. Data moved = 8 × 4 bytes = 32 bytes, so effective rate = 32 bytes / 300 ns ≈ 107 MB/s (approaching the 132 MB/s peak of a 33-MHz 32-bit PCI bus once the two-cycle address overhead is amortised over a longer burst).
