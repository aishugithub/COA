How the pipeline is actually built
We've drawn the pipeline as five neat boxes. But what hardware sits in each box, and what passes between them every clock? Time to open the machine.

Pipeline organization

Under the hood · Each stage is separate hardware. Between them sit registers — the interstage buffers B1–B4 — that latch one instruction's work and hand it to the next stage.
Figure 6.2 — A five-stage pipeline built from stage hardware + interstage buffers.

What each buffer hands forward

Follow the work · Each buffer carries exactly what the next stage needs — data, register identifiers, and the control signals that tell that stage what to do.
  • B1 → the newly fetched instruction, ready to decode.
  • B2 → the two operands read from registers, the immediate value, and the control signals for the remaining stages.
  • B3 → the ALU result (or the address/data for a memory access).
  • B4 → the value to be written back into the register file.
  • Control signals ride along with each instruction — this is pipelined control.
🔑
Each stage is its own hardware;
the interstage buffers hand the work forward on every clock.
CHAPTER 2
2
Datapath & control considerations
Overlap only works if no two stages ever fight over the same piece of hardware. What happens when they do — and how do we prevent it?

Every stage needs its own hardware

Why · If two stages shared a unit, they couldn't both work in the same cycle — the whole point of overlap would be lost. So the datapath is replicated per stage.
  • Separate hardware in each stage → all five instructions advance simultaneously.
  • Each stage also owns a buffer register to hold its result for the next stage.
  • Pipelined control: control signals are generated once (in Decode) and travel with the instruction down the pipe — not regenerated each stage.
  • But some resources are expensive to duplicate — like memory. That's where trouble starts…

Structural hazard — two stages, one resource

The clash · A single memory serves both Fetch (every cycle) and Memory access (for loads/stores). In the same cycle they collide — one must stall.
§6.7 — Separate instruction & data caches remove the structural hazard.

How many stages? A trade-off

Deeper isn't free · An n-stage pipeline can raise throughput up to n×. So why not 50 stages? Because each extra stage brings its own costs.
  • More stages → less work per stage → shorter clock period → higher clock rate.
  • But: more instructions in flight → more dependencies → more stalls.
  • And: the branch penalty grows if the decision moves to a later stage.
  • Gains diminish beyond a point — real designs balance depth against hazard cost (modern CPUs: ~10–20 stages, several GHz).
🔑
Give every stage its own hardware —
and duplicate the shared resources that would otherwise clash.

Influence on the instruction set
The pipeline runs smoothest on simple, regular instructions. So the desire to pipeline actually reshaped how instruction sets are designed. That's the RISC story.

Pipelining rewards simple instructions

Design for the pipe · The five-stage pipeline was tailored to RISC-style instructions. A few regularities make Fetch and Decode fast and every stage predictable.
  • Uniform length (one word) & few formats → simple, fast Fetch and Decode.
  • Load–Store architecture: only Load/Store touch memory; arithmetic is register-to-register → predictable stage timing.
  • Simple, regular addressing → the operand stage's control logic stays simple.
  • These are exactly the principles of RISC — which evolved hand-in-hand with pipelining.

Where complex instructions fight the pipe

The friction · CISC-style features — variable length, multiple memory operands, complex addressing — break the pipeline's regular rhythm. One culprit: side effects.
Move R5, (R8)+    auto-increment
Writes R5 and also changes R8 — an extra, hidden dependency.
  • A side effect changes a location other than the named destination (here, R8).
  • A later instruction using R8 now has a dependency the hardware must catch — extra stall / forward logic.
  • Variable-length instructions may take several cycles just to fetch — stalling the front end.

Condition codes, and how modern CPUs cope

Another side effect · A Compare sets condition-code flags that a later Branch silently depends on — an implicit dependency the pipeline must track.
Compare R7, R8
Branch>0 TARGET    depends on the flags Compare set
  • Flags are easy in a simple pipeline (one ALU op per cycle) but messy when many instructions are in flight.
  • Modern CPUs keep CISC instruction sets but crack each into simple RISC-like micro-operations internally — best of both worlds.

The instruction set and the pipeline are designed together.
Simplicity and regularity are what make overlap pay off.
