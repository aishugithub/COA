The assembly line

Pipeline organization — the five stages as hardware

Under the hood · Each stage is separate hardware. Between them sit registers — the interstage buffers B1–B4 — that latch one instruction's work and hand it to the next stage.
Figure 6.2 — A five-stage pipeline built from stage hardware and interstage buffers.

What each buffer hands forward

Follow the work · Each buffer carries exactly what the next stage needs — data, register identifiers, and the control signals that tell that stage what to do.
  • B1 → the newly fetched instruction, ready to decode.
  • B2 → operands read from registers, the immediate value, and the control signals for later stages.
  • B3 → the ALU result (or the address / data for a memory access).
  • B4 → the value to be written back into the register file.
  • Control signals travel with the instruction — this is pipelined control (revisited in Chapter 6).

Pipeline Performance
If overlapping k stages lets a new instruction finish every cycle, how much faster is that, really — and what stops us reaching the full k-fold gain?
Hamacher §6.8 · Performance evaluation (the basics)

Counting the cycles

The payoff · A pipeline of k stages fills up in k cycles, then finishes one instruction per cycle. Put numbers to the staircase.
  • k stages, n instructions → k + (n − 1) cycles  versus  k × n with no overlap.
  • Concrete: n = 100, k = 5 → 104 cycles instead of 500  ≈  4.8× faster.
  • Speedup approaches k (the number of stages) as n grows large.

The basic performance equation

Formally · Execution time depends on how many instructions run, the average cycles each takes, and the clock rate. Throughput is instructions completed per second.
T = ( N × S ) / R N = instructions · S = average cycles per instruction · R = clock rate
Throughput  Pnp = R / S  →  ideal pipeline (S = 1):  Pp = R Non-pipelined S = 5; ideal pipelining drops S to 1 → up to a 5× throughput gain.

How deep should the pipeline be?

Diminishing returns · An n-stage pipeline promises up to n× throughput. So why not 50 stages? Each extra stage brings costs that scale against depth.
  • More stages → less work per stage → shorter clock period → higher clock rate.
  • But more instructions in flight → more dependencies → more stalls.
  • And the branch penalty grows if the decision moves to a later stage.
  • The clock is ultimately limited by the slowest basic operation (usually the ALU). Real designs: ~10–20 stages.
🔑
Ideal speedup approaches the number of stages.
Every stall pulls the real gain below that ideal — which is what the rest of the unit is about.

The Role of Cache Memory
The pipeline is built to consume a memory word every single cycle. Main memory is far too slow to keep up — so a small, fast cache is what makes the whole pipeline possible.
Hamacher §6.2, §6.8.1 · Syllabus CO3: role of cache memory
🎤 Ask the class
The pipeline needs an instruction word every cycle — and data words too. If main memory takes ~100 cycles to answer, how can the pipeline ever run at one instruction per cycle?
It can't — unless a much faster memory sits in front of it. That fast buffer is the cache: on a hit it answers in about one cycle, so the pipeline keeps flowing; main memory is touched only on the rarer miss.

Why the pipeline needs a cache

The speed gap · Every cycle, Fetch reads an instruction; about one instruction in three is a Load/Store that touches data too. Main memory answers in tens of cycles — so without a fast memory in front, the pipe would stall almost constantly.
L1 cache (hit)
~1 cycle
L2 / L3 cache
~10 cycles
Main memory (DRAM)
~100 cycles
A cache bridges a ~100× speed gap — without it, "one instruction per cycle" is simply impossible.

The memory hierarchy

Fast-but-small over big-but-slow · No single memory is both huge and fast, so we stack them: each level keeps the most-used data of the level below. The CPU sees nearly the speed of the top and the size of the bottom.
faster ↑
bigger, slower ↓
Registers — <1 cycle · ~1 KB
L1 / L2 / L3 Cache (SRAM) — 1–30 cycles · KB–MB
Main memory (DRAM) — ~100 cycles · GB
Secondary storage (SSD / disk) — 10⁵–10⁶ cycles · TB+
The cache is the level that sits between the CPU and main memory — holding the blocks the pipeline is using now.

Locality — why a small cache works

Programs are predictable · A tiny cache can capture most accesses because programs reuse the same few locations, and the ones right next to them — the principle of locality.

Temporal locality

  • Reuse the same location again soon — a loop counter, a running sum, the top of the stack.
  • Keep a just-used block → the next reuse is a hit.

Spatial locality

  • Use locations near the last one — array elements, the next instruction in sequence.
  • Fetch a whole block (several words) at once → the neighbours are already there.
for (i = 0; i < N; i++) sum += A[i];
sum, i reused each pass → temporal · A[i], A[i+1]… are neighbours → spatial

Hit, miss, and average access time

Put a number on it · On a hit the cache answers in ~1 cycle and the pipe flows; on a miss we pay a full trip to main memory. The hit rate decides the average.
tavg = thit + (1 − h) × pmiss
  • h = hit rate  ·  pmiss = miss penalty (cycles to reach main memory).
  • Example: thit = 1, h = 0.95, pmiss = 100  →  tavg = 1 + 0.05 × 100 = 6 cycles.
  • Even a 95% hit rate costs 6× the hit time — which is why raising the hit rate matters more than almost anything else.

Cache in the pipeline

Back to the pipe · The cache is what actually lets the pipeline sustain one instruction per cycle — and its misses are the biggest stall term of all.
  • On a hit, Fetch and Memory each finish in one cycle → the pipe keeps its one-per-cycle rhythm.
  • Separate I-cache & D-cache (a Harvard split) let Fetch and a Load/Store use memory in the same cycle — removing the structural hazard.
  • On a miss, the whole in-order pipe stalls until main memory answers — non-deterministic, and it cannot be scheduled away.
δmiss = (mi + d × md) × pm = (0.05 + 0.30 × 0.10) × 10 = 0.8
Hamacher's numbers again: the cache-miss term (0.8) dwarfs the branch and load-use terms — usually the dominant penalty.
🔑
A cache makes a slow main memory look fast —
locality is why it works, and it is what lets the pipeline truly reach one instruction per cycle.

Instruction (Control) Hazards
A data hazard made one instruction wait. A branch is nastier: the pipeline doesn't even know which instruction to fetch next — so it may fetch the wrong ones entirely.
Hamacher §6.6 · Branch delays & branch prediction

The pipeline fetches ahead — and may guess wrong

The gap · To stay full, the pipeline fetches the next in sequence every cycle. But a branch can redirect execution — so those already-fetched instructions may be wrong.
  • A branch changes which instruction runs next (loops, if-else, calls).
  • But the branch must be executed before we know the outcome and the target address.
  • Meanwhile the pipeline has already fetched the instructions behind it — which must be discarded. That waste is a control hazard.

Conditional branches — test early too

One more move · For a conditional branch such as Branch_if_[R5]=[R6] LOOP, the comparison must also be done early.

  • This gives a common one-cycle penalty for all branch instructions.

Static prediction — a fixed guess

Simplest first · Guess the same way every time, decided before the program runs. If right, no penalty; if wrong, pay the penalty and refetch.
  • Assume not-taken: keep fetching in sequence — but only ~50% right for a coin-flip branch.
  • Use the branch direction: a backward branch (loop end) is usually taken; predict by the sign of the offset.
  • A single hint bit in the instruction lets the compiler say "expect taken / not-taken".

Dynamic prediction — learn from history

Do better · Keep 2 bits of history. A confident (strong) prediction survives one surprise — it takes two misses in a row to flip. But from a weak state a single surprise jumps straight to the opposite strong state.
Figure 6.12(b) — Hamacher's 4-state predictor. A weak miss jumps to the opposite strong state; a strong state needs two misses in a row to flip. BT = branch taken · BNT = branch not taken.

Influence on Instruction Sets
The pipeline runs smoothest on simple, regular instructions. So the wish to pipeline actually reshaped how instruction sets are designed — that is the RISC story.
Hamacher §6.10 · Pipelining and the instruction set
🎤 Ask the class
Every instruction runs on the same five stages. So why should the shape of an instruction — its length, its operands — matter to how fast the pipeline runs?
Because the stages are only as fast as their slowest, least predictable job. If Fetch can't tell where the next instruction ends, or if Decode finds three memory operands to arrange, the neat one-cycle-per-stage rhythm breaks — and every following instruction waits.

Simple instructions vs complex ones

Design for the pipe · The five-stage pipeline was tailored to RISC-style instructions. Regularity keeps Fetch and Decode fast and every stage predictable.

RISC — pipeline-friendly

  • Uniform length (one word), few formats → fast, fixed-time Fetch/Decode
  • Load–Store architecture: only Load/Store touch memory; arithmetic is register-to-register
  • Simple, regular addressing → simple operand-stage control, predictable timing

CISC — pipeline friction

  • Variable length → several cycles just to fetch one instruction
  • Multiple memory operands per instruction → extra stalls
  • Complex addressing → side effects & condition codes (hidden dependencies)

Why uniform length helps Fetch

Watch the pointer · Fetch must find where the next instruction ends before it can start the one after. Fixed length makes that trivial; variable length makes Fetch lurch.

Side effects fight the pipe

The hidden dependency · A side effect changes a location other than the named destination — an extra dependency the hazard logic must catch, on top of the obvious one.
Move R5, (R8)+    auto-increment
Writes R5 — and also changes R8. Two writes, one instruction.
  • A later instruction using R8 now has a dependency the compiler never wrote — it needs extra stall / forward logic.
  • Condition codes are another side effect: a Compare sets flags that a later Branch silently depends on.
  • More possible side effects = more hidden dependencies = more hazard hardware. RISC simply bans them.

Datapath & Control Considerations
Overlap only works if no two stages ever fight over the same hardware — and if we can put honest numbers on every stall we have met so far.
Hamacher §6.2, §6.7, §6.8.1 · Structural hazards & quantified penalties

Every stage needs its own hardware

Why · If two stages shared one unit, they could not both work in the same cycle — the overlap we bought in Ch 1 would be lost. So the datapath is replicated per stage.
  • Separate hardware in each stage → all five instructions can advance simultaneously.
  • Each stage owns a buffer register (B1–B4) that holds its result for the next stage to pick up.
  • Pipelined control: the control signals are generated once in Decode and travel with the instruction down the pipe — each stage reads the signals meant for it.
🎤 Ask the class
Fetch reads from memory every cycle. A Load also reads memory in its Memory stage. If there is only one memory, what happens when both want it in the same cycle?
They collide — and one must wait. This is a brand-new kind of hazard: not about data, not about branches, but about two stages needing the same physical resource. We call it a structural hazard.

Structural hazard — two stages, one resource

The clash · A single memory serves both Fetch (every cycle) and Memory access (loads/stores). In the same cycle they collide — one must stall. The cure: give each its own cache.
§6.7 — Separate instruction & data caches remove the structural hazard.

Putting numbers on the stalls

Honest accounting · The ideal is S = 1 cycle per instruction. Each kind of stall we met adds a penalty term — and these terms simply add up (Hamacher §6.8.1).
S = 1 + δstall + δbranch + δmiss
  • δstall — load-use hazards (data): frequency × penalty.
  • δbranch — branch mispredictions (control).
  • δmiss — cache misses (memory) — usually the biggest term of all.

Which stall hurts most?

Reveal & compare · Plug in typical numbers. Each bar is one term's contribution to S. Watch which one dwarfs the others — it tells you where to spend design effort.

0.25×0.40×1 = 0.10  ·  0.20×0.10×1 = 0.02  ·  (0.05 + 0.30×0.10)×10 = 0.80  →  the cache miss dominates.

Worked example 6.2 — branch penalty

Trace it together · A program is 20% branches, with static not-taken prediction (1-cycle penalty when a branch is taken), no other stalls. How much does the taken-rate matter?
  • Penalty only when a branch is actually taken:   δbranch = 0.20 × (fraction taken) × 1.
  • 30% taken: δbranch = 0.20 × 0.30 = 0.06  →  S = 1.06.
  • 70% taken: δbranch = 0.20 × 0.70 = 0.14  →  S = 1.14.
  • The 70%-taken program is slower by (1.14 / 1.06 − 1) × 100 ≈ 7.5% — the same code, just more branches taken.
🔑
Give every stage its own hardware; duplicate the shared resources that clash —
and when you total the stalls, the cache-miss term usually dominates.

Superscalar Operation
A single pipeline can finish, at best, one instruction every cycle. To go faster still, we stop waiting in one line — and open several checkouts at once.
Hamacher §6.9 · Multiple issue & out-of-order execution

The ceiling — and how to break it

The analogy · A perfect pipeline is one queue, one till: at best one customer leaves per beat. Want more throughput? Open a second till — serve two lines at once.

Multiple issue — more than one per cycle

Break the ceiling · A superscalar processor equips itself with several execution units and issues multiple instructions each cycle — the hardware version of the second till.
  • The fetch unit fetches two or more instructions every cycle into an instruction queue.
  • A dispatch unit sends independent instructions to different execution units.
  • Throughput can now exceed one instruction per cycle — this is multiple issue.

🎤 Ask the class
With several units running at once, a later instruction may finish before an earlier one. How do we still get the correct answer — and a clean picture if an exception fires?
Let them execute out of order, but commit in order. Extra bookkeeping hardware — reservation stations, register renaming, and a reorder buffer — lets results finish early yet be made visible strictly in program order.

Keeping many-in-flight correct

The price of parallelism · Running many instructions at once means they may finish out of order. Four mechanisms keep the results correct and the exceptions precise.
  • Reservation stations — hold a dispatched instruction until all its operands have arrived.
  • Out-of-order execution — an independent instruction runs the moment it is ready, not in line order.
  • Register renaming — temporary registers remove false conflicts (two instructions reusing a name).
  • Reorder buffer — commits results strictly in program order → precise exceptions.
