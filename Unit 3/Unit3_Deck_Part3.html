The branch problem
A data hazard made one instruction wait. A branch is nastier: the pipeline doesn't even know which instruction to fetch next — so it may fetch the wrong ones entirely.

The pipeline fetches ahead — and may guess wrong

The gap · To stay full, the pipeline fetches the next in sequence every cycle. But a branch can redirect execution — so those already-fetched instructions may be wrong.
  • A branch instruction can change which instruction runs next (e.g. loops, if-else, function calls).
  • But the branch must be executed before we know the outcome and the target address.
  • Meanwhile the pipeline has already fetched the instructions sitting right behind it — which now have to be thrown away. That waste is a control hazard.

Shrinking the penalty
If the damage is the instructions fetched before we know the branch outcome — then deciding the branch sooner should hurt less. How soon can we decide?

Decide in Decode — penalty drops to one

The fix · Add a small comparator and an adder so the branch condition and target are worked out in the Decode stage. Now only one wrong instruction is fetched.

CHAPTER 3
3
Guessing ahead: branch prediction
Even a one-cycle penalty adds up over millions of branches. What if the processor could guess the outcome the instant it fetches the branch — and usually be right?

Static prediction — a fixed guess

Simplest first · Guess the same way every time, decided before the program runs. If right, no penalty; if wrong, pay the usual penalty and refetch.
  • Assume not-taken: keep fetching in sequence. Simple — but only ~50% right for a coin-flip branch.
  • Use the branch direction: a backward branch (end of a loop) is usually taken; a forward branch usually not. Predict by the sign of the offset.
  • A single hint bit in the instruction lets the compiler say "expect taken / not-taken".

Dynamic prediction — learn from history

Do better · Track how this branch behaved last time. A 2-bit counter needs two wrong guesses in a row to change its mind — so one odd iteration won't fool it.
Figure 6.12 — A 2-bit predictor: it only flips its guess after two misses in a row.
🎤 Ask the class
Predict · A loop runs 100 times, so its branch is taken 99 times and not taken once (the exit).
With the 2-bit predictor, about how many of those 100 branches are mispredicted?
Just ~1 — the loop exit. The single not-taken pass isn't enough to flip a strongly-taken counter, so every looping pass is predicted correctly.

Predicting in cycle 1 — the branch target buffer

The last piece · To fetch the right instruction next cycle, we must predict while still fetching the branch — before we even know it's a branch.
  • A branch target buffer (BTB) is a small fast table, keyed by the branch's address.
  • Each entry stores the prediction state bits and the target address.
  • While fetching, the processor checks the BTB: a hit gives both "this is a taken branch" and where to go — so the right instruction is fetched next cycle. (~1024 entries, most-recent branches.)
