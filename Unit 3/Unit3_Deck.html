Pipeline performance — counting the cycles

The payoff · Put numbers to the staircase. A pipeline of k stages fills up in k cycles, then finishes one instruction per cycle after that.
  • k stages, n instructions → k + (n − 1) cycles  — versus  k × n cycles with no overlap.
  • Concrete: n = 100, k = 5 → 104 cycles instead of 500  ≈  4.8× faster.
  • Speedup approaches k (the number of stages) as n grows large.

Speedup approaches k — but never quite reaches it

Why not perfect · Ideal throughput is one instruction per cycle, a k-fold gain. Two things always hold us back.
  • Filling & draining — the first k−1 and last few cycles aren't at full overlap.
  • The slowest stage sets the clock — every stage must fit the longest stage's delay.
  • And any stall — a stage forced to wait — drops throughput below the ideal. Which brings us to hazards…
🔑
Pipelining does not make one instruction faster.
It raises throughput — how many finish per second — by overlapping many.

When the flow breaks: the data hazard
Instruction 2 needs a number that instruction 1 hasn't finished writing yet. Read it now, and you read a stale value. Now what?

A dependency between neighbours

The catch · The staircase quietly assumed instructions are independent. But real code chains: one instruction's result feeds the next. Watch register R2.
Add     R2, R3, #100    R2 ← [R3] + 100
Subtract R9, R2, #30    R9 ← [R2] − 30
  • R2 is produced by the Add and consumed by the Subtract — a data dependency on R2.
  • Fine when they run one at a time. The trouble starts when we overlap them…
