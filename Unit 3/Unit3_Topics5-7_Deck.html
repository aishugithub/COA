5
Influence on Instruction Sets
The pipeline runs smoothest on simple, regular instructions. So the wish to pipeline actually reshaped how instruction sets are designed — that is the RISC story.
Hamacher §6.10 · Pipelining and the instruction set
🎤 Ask the class
Every instruction runs on the same five stages. So why should the shape of an instruction — its length, its operands — matter to how fast the pipeline runs?
Because the stages are only as fast as their slowest, least predictable job. If Fetch can't tell where the next instruction ends, or if Decode finds three memory operands to arrange, the neat one-cycle-per-stage rhythm breaks — and every following instruction waits.

Simple instructions vs complex ones

Design for the pipe · The five-stage pipeline was tailored to RISC-style instructions. Regularity keeps Fetch and Decode fast and every stage predictable.

RISC — pipeline-friendly

  • Uniform length (one word), few formats → fast, fixed-time Fetch/Decode
  • Load–Store architecture: only Load/Store touch memory; arithmetic is register-to-register
  • Simple, regular addressing → simple operand-stage control, predictable timing

CISC — pipeline friction

  • Variable length → several cycles just to fetch one instruction
  • Multiple memory operands per instruction → extra stalls
  • Complex addressing → side effects & condition codes (hidden dependencies)

Why uniform length helps Fetch

Watch the pointer · Fetch must find where the next instruction ends before it can start the one after. Fixed length makes that trivial; variable length makes Fetch lurch.

Side effects fight the pipe

The hidden dependency · A side effect changes a location other than the named destination — an extra dependency the hazard logic must catch, on top of the obvious one.
Move R5, (R8)+    auto-increment
Writes R5 — and also changes R8. Two writes, one instruction.
  • A later instruction using R8 now has a dependency the compiler never wrote — it needs extra stall / forward logic.
  • Condition codes are another side effect: a Compare sets flags that a later Branch silently depends on.
  • More possible side effects = more hidden dependencies = more hazard hardware. RISC simply bans them.

Modern CPUs: keep CISC, crack it inside

The compromise · Real x86 chips keep the familiar CISC instruction set for compatibility, but internally crack each instruction into simple RISC-like micro-operations — then pipeline those.
one CISC instruction
→
µop 1 · load
µop 2 · add
µop 3 · store
The messy instruction is split into a stream of clean micro-ops that flow through the pipeline.
🔑
The instruction set and the pipeline are designed together.
Simplicity and regularity — uniform length, load-store, simple addressing — are what make overlap pay off.

Datapath & Control Considerations
Overlap only works if no two stages ever fight over the same hardware — and if we can put honest numbers on every stall we have met so far.
Hamacher §6.2, §6.7, §6.8.1 · Structural hazards & quantified penalties

Every stage needs its own hardware

Why · If two stages shared one unit, they could not both work in the same cycle — the overlap we bought in Ch 1 would be lost. So the datapath is replicated per stage.
  • Separate hardware in each stage → all five instructions can advance simultaneously.
  • Each stage owns a buffer register (B1–B4) that holds its result for the next stage to pick up.
  • Pipelined control: the control signals are generated once in Decode and travel with the instruction down the pipe — each stage reads the signals meant for it.
🎤 Ask the class
Fetch reads from memory every cycle. A Load also reads memory in its Memory stage. If there is only one memory, what happens when both want it in the same cycle?
They collide — and one must wait. This is a brand-new kind of hazard: not about data, not about branches, but about two stages needing the same physical resource. We call it a structural hazard.

Structural hazard — two stages, one resource

The clash · A single memory serves both Fetch (every cycle) and Memory access (loads/stores). In the same cycle they collide — one must stall. The cure: give each its own cache.
§6.7 — Separate instruction & data caches remove the structural hazard.

Putting numbers on the stalls

Honest accounting · The ideal is S = 1 cycle per instruction. Each kind of stall we met adds a penalty term — and these terms simply add up (Hamacher §6.8.1).
S = 1 + δstall + δbranch + δmiss
  • δstall — load-use hazards (data): frequency × penalty.
  • δbranch — branch mispredictions (control).
  • δmiss — cache misses (memory) — usually the biggest term of all.

Worked example 6.2 — branch penalty

Trace it together · A program is 20% branches, with static not-taken prediction (1-cycle penalty when a branch is taken), no other stalls. How much does the taken-rate matter?
  • Penalty only when a branch is actually taken:   δbranch = 0.20 × (fraction taken) × 1.
  • 30% taken: δbranch = 0.20 × 0.30 = 0.06  →  S = 1.06.
  • 70% taken: δbranch = 0.20 × 0.70 = 0.14  →  S = 1.14.
  • The 70%-taken program is slower by (1.14 / 1.06 − 1) × 100 ≈ 7.5% — the same code, just more branches taken.
🔑
Give every stage its own hardware; duplicate the shared resources that clash —
and when you total the stalls, the cache-miss term usually dominates.

Superscalar Operation
A single pipeline can finish, at best, one instruction every cycle. To go faster still, we stop waiting in one line — and open several checkouts at once.
Hamacher §6.9 · Multiple issue & out-of-order execution

The ceiling — and how to break it

The analogy · A perfect pipeline is one queue, one till: at best one customer leaves per beat. Want more throughput? Open a second till — serve two lines at once.

Multiple issue — more than one per cycle

Break the ceiling · A superscalar processor equips itself with several execution units and issues multiple instructions each cycle — the hardware version of the second till.
  • The fetch unit fetches two or more instructions every cycle into an instruction queue.
  • A dispatch unit sends independent instructions to different execution units.
  • Throughput can now exceed one instruction per cycle — this is multiple issue.

🎤 Ask the class
With several units running at once, a later instruction may finish before an earlier one. How do we still get the correct answer — and a clean picture if an exception fires?
Let them execute out of order, but commit in order. Extra bookkeeping hardware — reservation stations, register renaming, and a reorder buffer — lets results finish early yet be made visible strictly in program order.

Keeping many-in-flight correct

The price of parallelism · Running many instructions at once means they may finish out of order. Four mechanisms keep the results correct and the exceptions precise.
  • Reservation stations — hold a dispatched instruction until all its operands have arrived.
  • Out-of-order execution — an independent instruction runs the moment it is ready, not in line order.
  • Register renaming — temporary registers remove false conflicts (two instructions reusing a name).
  • Reorder buffer — commits results strictly in program order → precise exceptions.
